## Ключевые решения (пронумерованы, ссылаться как ADR-N)

1. **Свой рантайм, без Agones/K8s** — разбор в `04`. Talos отпал; ОС тачек — Ubuntu LTS (Flatcar — опция позже).
2. **Go для master и agent**; статические бинари; systemd.
3. **Postgres — единственный state store.** Матчи/сервера/ноды/версии — в PG; матчмейкинг-тикеты — in-memory (теряются при рестарте, клиент ретраит — это осознанно).
4. **Один master на старте — принятый SPOF**: при падении текущие матчи живут (коннект прямой), страдает только создание новых. Рестарт ≤ секунд, state в PG.
5. **Агент дозванивается до master** (outbound gRPC bidi поверх mTLS): тачкам не нужен входящий admin-порт, master — единственный публичный адрес управления.
6. **Дедики — контейнеры containerd** (cgroups-лимиты против noisy neighbor, чистые мультиверсии, дешёвый rollback). Host network, порты из пула 20000–29999.
7. **liba ↔ agent — NDJSON поверх per-server unix socket**, сокет bind-mount'ится в контейнер. Identity дедика = его сокет; никакой сети и токенов внутри.
8. **Граница allocation API внутри master**: матчмейкер — потребитель, флот — поставщик. Живут в одном процессе, но интерфейс жёсткий (и публично доступен) — чтобы чужой матчмейкинг и вынос в отдельный процесс были дёшевы.
9. **Панель — клиент публичного REST API** (+SSE), статика в бинаре master (go:embed). Никаких приватных лазеек. Машиночитаемый контракт (OpenAPI 3.1) у API ЕСТЬ — `master/api/openapi.yaml`, — и заведён он ровно тем способом, что предписывал #972: генерацией из таблицы маршрутов с CI-гейтом на расхождение. Источник правды остался один: роутер регистрируется ИЗ ТАБЛИЦЫ (`master/internal/httpapi/routes.go`), из неё же собирается спека, так что ручка вне таблицы попросту не отвечает. Подробности — `master.md` §6.
10. **Ansible ставит тачки и агентов; жизнью дедиков управляет только master/agent-цикл.** IaC (Terraform) не делаем.
11. **Session-based only, Linux-only** (решения 07.07.2026). Дедик умер → слот пересоздаётся; ничего не «лечим».
12. **MIT** для всего стека (решение 07.07.2026).

## Основные потоки

1. **Деплой версии**: CI собирает образ → push GHCR → `POST /v1/versions` → `POST /v1/deploy` → master шлёт агентам PrePull → все тачки прогрели образ → master активирует версию → новые матчи на новой, старые дедики доигрывают → reap. Подробно: `master.md` §Deploy.
2. **Матч**: клиент меряет QoS-пинги → `POST /v1/matchmaking/tickets` → матчмейкер собирает матч → внутренний `allocate(region, version)` (SKIP LOCKED по ready-серверам) → agent уже держит дедик готовым → клиентам отдаётся `host:port` → игроки коннектятся напрямую.
3. **Heartbeat**: liba шлёт players/tick в agent (UDS) → agent агрегирует и шлёт master (gRPC, каждые 2с) → master обновляет PG + отдаёт live в панель (SSE).
4. **Отказ тачки**: heartbeat молчит >10с → карантин: сервера тачки → `failed`, аллокации с неё исключены, буфер восстанавливается на живых; алерт.
5. **Drain**: `POST /v1/nodes/{id}/drain` → новые дедики не создаются, ready-пул тачки reap'ится, allocated доигрывают → тачка пустая → можно снимать.
6. **Рестарт master**: systemd перезапуск ≤ секунд; агенты переподключаются с бэкоффом; in-flight тикеты потеряны (клиент ретраит), матчи и сервера — в PG, ничего не рвётся.

## Модель доверия (trust boundaries)

birdman — инфраструктура дедиков, а не identity-платформа: **конечный игрок в birdman не аутентифицируется вообще** и по дизайну не должен — аутентификация игрока и аккаунты записаны в «Явно вне скоупа (v1)» вместе с анти-абьюзом. Аутентифицированы только вызывающие со стороны инфраструктуры:

| Кто | Чем аутентифицирован | Где |
|---|---|---|
| оператор / сервис (CI, бэкенд игры, `mmcli`) | API-ключ `Authorization: Bearer` + скоуп из `{admin, deploy, matchmaking, allocate, readonly}` (`admin` включает остальные); ключ может быть привязан к паре (project, env) | `httpapi/auth.go` |
| панель (браузер) | cookie-сессия того же ключа + заголовок `X-Birdman-Csrf` на не-GET/HEAD (проверяется только наличие заголовка; от cross-site защищает `SameSite=Lax`) | `httpapi/{session,auth}.go` |
| нода (агент) | клиентский mTLS-серт внутренней CA, полученный по `node_token` — **строго только в режиме `agentlink_auth: mtls`**; дефолт конфига `mixed` принимает и голый `node_token` (`master.md` §7, `protocol.md` §1) | `internal/agentlink` |
| дедик (liba) | ничем: identity = его per-server unix-сокет. Гарантию даёт бинд-маунт (в контейнер виден только его собственный каталог, `protocol.md` §2), а не сам сокет: он 0666 и пира не проверяет — что-то запущенное на ноде вне этого маунта может представиться либой чужого дедика | `agent/internal/uds` |
| **игрок** | **ничем — границы нет** | — |

Без аутентификации на листенере API отвечают две ручки: `GET /healthz` и `GET /v1/qos` — вторая по замыслу публичная и отдаёт адреса живых нод (`httpapi/server.go`). Третья, `GET /metrics` (весь Prometheus-реестр), с tracker #1003 на этом листенере НЕ живёт: она уехала на свой адрес (`listen_metrics`, деф. `127.0.0.1:9102`), потому что реестр перечисляет слаги проектов, имена окружений и живые `server_id` — данные, закрытые на `/v1/*` арендаторской границей #993. Аутентификации у неё по-прежнему нет (скрейперу нечем носить ключ) — границей служит адрес, и теперь это свойство КОДА, а не конфига прокси.

`player_id` в тикете (`POST /v1/matchmaking/tickets`) — **непрозрачная строка от вызывающего**, master ей доверяет: единственная валидация — непустая (`httpapi/matchmaking.go`, `matchmaker/matchmaker.go`), связи с аккаунтом нет. На что она влияет: анти-дубль «один активный тикет на (project, env, player_id)», rate-limit 5 rps на `player_id`, подпись `join_token` — и всё; на подбор группы она не влияет вовсе (группа — старейшие `match_size` тикетов очереди, `matchmaker/tick.go`). Обратно она возвращается в теле любого чтения тикета. **В БД не персистится**: колонки `player_id` нет ни в одной таблице, `RecordMatch` пишет только матч/сервер/версию/регион/env (`store/matchmaking.go`, `migrations/000001_init.up.sql`) — игроки доходят до БД только счётчиками (`servers.players`, `matches.players_peak` и роллапы статистики). В памяти master'а тикет вместе с `player_id` переживает свой терминальный статус ещё на `max(2×ticket_ttl, 5м)` — при дефолтном TTL это 5 минут (`matchmaker/matchmaker.go`), и всё это время он читается по `ticket_id`.

**Предусловие эксплуатации: тикеты заводит бэкенд игры, а не игровой клиент.** Ключ со скоупом `matchmaking` — общий секрет, и он даёт больше, чем кажется: завести тикет с ЛЮБЫМ `player_id`; зная `ticket_id`, прочитать чужой тикет (а после матча — и его `{host, port, match_id, join_token?}`) и отменить его — проверки владения тикетом нет; а тикет с чужим `player_id` вдобавок вытесняет в `cancelled` ещё не сматченный тикет настоящего владельца этого id в том же (project, env) (анти-дубль). **Единственное, что это ограничивает, — привязка ключа к (project, env), и с tracker #963 она проверяется на ВСЕХ трёх ручках тикетов, а не только на создании** (`httpapi/matchmaking.go`): привязанный ключ читает и отменяет лишь тикеты своей пары, на чужой получает `404` — тем же телом, что и на несуществующий `ticket_id` (не 403: иначе ручка стала бы оракулом существования чужих тикетов), причём гейт стоит ДО rate-limit'а, который ключуется по `player_id` ЖЕРТВЫ. Что привязка НЕ ограничивает: внутри своей пары владения тикетом по-прежнему нет (осознанно, v0), а глобальный (непривязанный) ключ достаёт до всех проектов и окружений — привязка опциональна by design. Отсюда схема:

1. игрока аутентифицирует бэкенд игры своим механизмом (birdman про этот механизм ничего не знает);
2. `matchmaking`-ключ лежит у бэкенда и наружу не уезжает;
3. бэкенд заводит тикет с уже проверенным `player_id` и отдаёт игроку результат матчмейкинга.

Если ключ всё-таки вшит в игровой клиент (к этому подталкивает клиентский матчмейкинг из `sdk.md` §3 — по спеке он ходит в master напрямую; сама UE-сабсистема пока черновик-заглушка, `BirdmanMatchmakingClient.h`), то ключ публичный, `player_id` — самопровозглашённый, и строить на нём нельзя ничего, кроме удобства: любой игрок может встать в очередь под чужим id и сбивать ему матчмейкинг. Rate-limit 5 rps в этом режиме — глушилка абьюза, а не граница безопасности (`httpapi/ratelimit.go`); он считается per `player_id`, in-memory в процессе master, то есть подставленный id обходит и его.

`join_token` = `base64url(match_id|player_id|exp)` + HMAC (`matchmaker/jointoken.go`) — **авторизация захода на конкретный дедик** («не зашёл мимо матчмейкера»), а НЕ аутентификация игрока: подпись доказывает, что эту пару (матч, игрок) выдал матчмейкер, но НЕ то, что предъявитель — тот самый игрок; перехваченный токен работает у любого. Payload подписан, но не шифрован — `player_id` внутри читается кем угодно. Выключен по умолчанию; TTL — 60с и из конфига не настраивается (`matchmaker.Config.JoinTokenTTL`), а при `enabled` без `BIRDMAN_MM_JOIN_SECRET` секрет эфемерный и токены не переживают рестарт master (`config.go`). И **на сегодня его не проверяет никто**: master только выдаёт (`VerifyJoinToken` — референс для будущей проверки, вызывается лишь из тестов), агент фрейм `verify_token` (`protocol.md` §2) не шлёт, а для liba это неизвестный тип, который она обязана игнорировать (`sdk/core/tests/golden_test.cpp`). Считать его действующей гарантией нельзя.

### Что birdman про игроков не знает: leave, reconnect, наблюдаемость

Прямое следствие того, что `player_id` не персистится: **ростера нет** — birdman не может ответить «в каком матче игрок X». Отсюда деление обязанностей.

- **Выход игрока (leave)** — целиком за игрой. В контракте liba есть только агрегат `players{count}` (`protocol.md` §2); агент лишь складывает его в состояние сервера и шлёт master'у heartbeat'ом (`agent/internal/daemon/manager.go`), явного leave-API нет. **Матч не завершается по «счётчик стал 0»** — такой логики нет ни в master, ни в агенте: конец матча объявляет игра (`NotifyMatchEnd`), после чего процесс дедика обязан завершиться сам, и только тогда агент увидит exit, а reconcile поднимет новый ready-дедик. Это обязанность игры по контракту (`sdk.md` §2), а не механизм birdman: игра, не вышедшая после `match_end`, оставляет сервер занятым навсегда.
- **Реконнект** — тоже за игрой и её бэкендом: матчмейкер реконнект не умеет и не притворяется (`matchmaker/matchmaker.go`, «explicitly out of v0: … reconnect»), новый тикет = новый матч, а не возврат в старый. Рабочая схема:
  1. обрыв связи при живом дедике — транспорт игры (`ClientTravel` на тот же `host:port`); birdman не участвует, адрес стабилен;
  2. клиент потерял адрес — его отдаёт бэкенд игры из своей записи `player_id → {match_id, host, port}` (эти поля бэкенд получил результатом матчмейкинга, `sdk.md` §3), после собственной аутентификации игрока. Сохранять для этого `join_token` бесполезно: он живёт 60с и перевыпустить его нечем — когда его проверка появится, реконнект потребует отдельного решения;
  3. жив ли матч — `GET /v1/matches/{id}` (скоуп readonly): `pending|running` — можно возвращаться, `finished|aborted` — в обычный матчмейкинг. Источник истины — именно состояние матча, а не `POST /v1/allocate`: он идемпотентен по `match_id` в пределах (project, env), но живость не проверяет — `servers.match_id` никогда не очищается, поэтому на давно законченный `match_id` он вернёт адрес уже реапнутого сервера (`store/allocate.go`, `master.md` §3).
- **Наблюдаемость матча** снаружи: match-level стейт birdman отдаёт — `GET /v1/events` и SSE `/v1/events/stream` (readonly) несут `match_start` и `match_end` (payload `result: completed|aborted`) с `match_id`; `GET /v1/matches/{id}` — то же поллингом плюс живой `server_players`. Две ловушки: (1) изменение счётчика игроков событием НЕ является — оно приезжает heartbeat'ом и видно только поллингом; (2) матч, оборванный смертью дедика, переводится в `aborted` без события `match_end`, а сопровождающее `server_failed` несёт `match_id` лишь в одном из четырёх путей — когда о смерти доложила сама liba (`failed`/`oom`); в остальных (`agent_report`, `node_lost`, `start_timeout`) в событии только `server_id`/`node_id` (+`version_id`), и фильтр по `match_id` его пропустит (`store/{heartbeat,servers}.go`). Авторитетный ответ на «матч ещё идёт?» — состояние матча, а не наличие события.
- **Player-level стейта** («вышел КОНКРЕТНО игрок X») в birdman нет вовсе, и структурированного канала для него не существует: строчку можно вытолкнуть фреймом `log` и потом искать её в логах дедика, но это лог, а не контракт. Источник такого потока — сам дедик, и идти он должен в бэкенд игры мимо birdman.

Осознанные ограничения v1: нет seat-awareness и бэкфилла (счётчик, а не список мест), матчмейкинг не reconnect-aware, `join_token` не проверяется (см. выше).

## Глоссарий

- **тачка / node** — bare-metal или VM с агентом; **дедик / server** — один процесс-контейнер игрового сервера; **слот** — единица capacity тачки (обычно 1 дедик = 1 слот, конфигурируемо); **матч** — игровая сессия на дедике; **буфер / warm pool** — ready-дедики, ждущие аллокации; **окно мультиверсий** — период, когда активны две версии (мягкий деплой); **drain** — вывод тачки/версии без обрыва матчей; **карантин** — тачка без heartbeat, исключена из аллокаций.

| Билд → живой сервер | <15 мин |

| Uptime прод-игр | 99.9% |

## Явно вне скоупа (v1)

Биллинг, free tier, **аутентификация конечного игрока и аккаунты** (см. «Модель доверия»: `player_id` — непрозрачная строка от бэкенда игры), анти-абьюз, Windows, персистентные миры, relays, скилловый матчмейкинг/пати, мульти-master HA, autoscale закупки тачек (добавление — ansible-командой вручную).

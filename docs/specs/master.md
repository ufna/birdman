create table events (                    -- аудит + лента для панели/алертов

create table api_keys (

## 2. Флот-контроллер (reconcile)

Цикл каждые **1с** (один воркер на project×region, advisory lock в PG на случай двух master'ов по ошибке):

```
desired  = fleet_configs (active_version + версии в окне мультиверсий, buffer_ready)
observed = servers where state in (creating, ready) group by version
for each version в окне:
  deficit = buffer - count(creating+ready) → создать deficit серверов:
      node = спред: наименее занятая active-нода региона первой,
             где free_slots > 0 и heartbeat свежий            -- анти-аффинити
      insert servers(state='creating') + команда агенту StartServer
  surplus (только у deprecated-версий или при buffer↓) → reap старейших ready
failed-сервера: слот освобождается сам (insert нового сделает дефицит)
crash-loop: ≥3 failed одной версии на одной тачке за 10 мин → стоп созданий
            этой пары (version,node) на 15 мин + event crash_loop
```

**Размещение буфера — анти-аффинити (follow-ups итерации 5 §1):** дефицит раскладывается на наименее занятые active-ноды региона первыми (`order by used asc`), растягивая warm-буфер по железу; нода на полной ёмкости (`used = capacity_slots`) из размещения исключается вовсе. Плотная упаковка (bin-pack, busier-node-first) **отвергнута учением 5.2** — спред снижает blast-radius отказа одной ноды (buffer_ready=2 над двумя пустыми нодами → 1+1, а не 2+0).

Создание сервера — это команда агенту; переход `creating → ready` делает только heartbeat от агента (после `ready` от liba). (Уточнено в v0: `creating` без прогресса от агента дольше 120с → `failed` + событие — самолечение после потери StartServer/рестарта master; репорт `pulling` от агента обновляет `updated_at` и таймер не срабатывает.)

## 3. Allocation API (граница матчмейкер ↔ флот)

`POST /v1/allocate {project, region, version_id?, match_id}` → `{server_id, host, port}` | `409 no_capacity`

```sql
with c as (
  select s.id from servers s
  join nodes n on n.id = s.node_id
  where s.project_id = $1 and s.state = 'ready'
    and s.version_id = coalesce($2, s.version_id)
    and n.region = $3 and n.state = 'active'
    and n.last_heartbeat_at > now() - interval '10 seconds'
  order by s.created_at
  limit 1
  for update of s skip locked
)
update servers set state='allocated', match_id=$4, updated_at=now()
where id = (select id from c)
returning id, node_id, port;
```

Свойства: атомарно, p95 <50мс, тысячи/с. Идемпотентность: повторный запрос с тем же `match_id` возвращает уже выданный сервер. `no_capacity` → матчмейкер держит тикеты и ретраит (буфер тем временем восстанавливается reconcile'ом).

## 4. Матчмейкер v0

- Тикет: `{ticket_id, player_id, client_version, regions: [{region, rtt_ms}]}`. Очереди **in-memory** per (region, compat-bucket). Потеря при рестарте — ок: клиент ре-квьюится (см. `sdk.md`). (Уточнено в v0: статусы тикета `queued | matched | update_required | cancelled | expired`; TTL тикета в очереди — конфиг `ticket_ttl_s`, деф. 120с → `expired`; терминальные тикеты живут в памяти ещё ~2×TTL для поздних GET.)
- Тик каждые **500мс**: в каждой очереди собрать группы по `match_size` (конфиг per project — колонка `projects.match_size`, деф. 2, правится `PUT /v1/projects/{slug}`; уточнено в v0) → `allocate` (внутренний вызов store с новым `match_id` uuid, регионом и пиненой версией) → всем участникам `matched {host, port, match_id, join_token?}`. `no_capacity` → тикеты остаются в очереди, ретрай следующим тиком (буфер тем временем поднимает reconcile); заодно инкрементится `birdman_allocation_failures_total{no_capacity}` — алерт BufferEmpty видит и внутренние отказы.
- Выбор региона: минимальный медианный rtt по группе (группа — старейшие `match_size` тикетов, FIFO; тай-брейк — имя региона); если очередь региона < match_size дольше `widen_after_s` (деф. 30с) — расширяем на следующий по rtt регион игрока (ещё один регион за каждый следующий интервал).
- `client_version` не входит ни в один compat-bucket активных версий → ответ `update_required` (проверка на submit и на каждом тике — смена активной версии не оставляет несовместимые тикеты висеть). (Уточнено в v0: правило по умолчанию major.minor из `ops.md` §3, overrides-таблица — позже; «активные версии» региона = `fleet_configs.active_version` окружения тикета (+ окно deprecated того же env — §Окружения; прежний ранг `versions(state=active, channel=prod)` снят вместе с `channel`), пока deploy-менеджер не переводит state — см. §5; при полном отсутствии активных версий тикеты ждут в очереди до TTL, а не получают `update_required`.)
- `join_token` = HMAC(match_id, player_id, exp 60с) — дедик проверяет через liba (анти-«зашёл мимо матчмейкера»); v0 — опционально, включается флагом (`matchmaking.join_token.enabled`, секрет — env `BIRDMAN_MM_JOIN_SECRET`; выдача реализована, проверка на дедике — TODO liba). Это **авторизация захода на дедик, а не аутентификация игрока**, и пока никем не проверяется: агент фрейм `verify_token` не шлёт, liba его игнорирует как неизвестный тип — гарантией считать нельзя (`architecture.md`, «Модель доверия»).
- Анти-дубль: один активный тикет на player_id (новый вытесняет старый → `cancelled`); ключ — (project, env, player_id), окружения игрока независимы.
- `player_id` — **непрозрачная строка от вызывающего**, master ей доверяет и нигде её не персистит; аутентификации игрока в birdman нет. Предусловие: тикеты заводит держатель `matchmaking`-ключа = бэкенд игры, не игровой клиент (ключ даёт право на ЛЮБОЙ `player_id`, а также чтение/отмену чужого тикета по `ticket_id`). Целиком — `architecture.md`, «Модель доверия (trust boundaries)».
- (Уточнено в v0.) Проект тикета: поле `project` опционально — по умолчанию `matchmaking.default_project` из конфига либо единственный проект в БД; успешная аллокация пишет строку в `matches` (state `pending`).
- Метрики: `birdman_mm_queue_depth{region,env}` (по лучшему региону тикета и окружению; environments v1 §7), `birdman_mm_time_to_match_seconds` (histogram), `birdman_mm_tickets_total{result}`.
- Явно вне v0: скиллы, пати, бэкфилл, реконнект в матч.

## 5. Deploy-менеджер (мягкий деплой)

Состояния версии: `registered → prepulling → active → deprecated → disabled`.

```
POST /v1/deploy {version_id}:
  1. version.state = prepulling; всем активным тачкам региона — PrePull(image)
  2. все тачки отчитались pulled (или таймаут 15 мин → abort + event)
  3. транзакция: старая active → deprecated; новая → active; fleet_config.active_version = new
  4. reconcile сам: поднимает буфер новой; deprecated-дедики новых матчей не получают
  5. reap deprecated: players==0 → stop; либо по reap_ttl_min — Drain с дедлайном (liba получает drain)
POST /v1/rollback: шаг 3 в обратную сторону (образы уже на тачках) — секунды
```

Окно мультиверсий: буферы считаются для **обеих** версий (active — полный buffer, deprecated — min(2, buffer)); учитывать при capacity-планировании тачек. Матчмейкер в окне матчит старых клиентов на deprecated, если политика `compat` разрешает (см. `ops.md` §Версии).

> **(Уточнено в v0, итерация 3 — deploy-менеджер реализован.)**
> - Состояния версий — **project-global**; на проект одновременно живёт максимум **одна** deprecated: при флипе более старые deprecated уходят в `disabled` (событие `version_disabled`). `disabled` недоступна для деплоя и матчинга.
> - Флип демотирует не только `state=active`, но и версию, на которую указывает `fleet_configs.active_version`, оставаясь `registered` (bootstrap через `PUT /v1/fleets` до появления deploy-менеджера) — иначе старый билд выпал бы из окна и его живые матчи получили бы drain немедленно.
> - **Окно закрывает `reap_ttl_min`**: по его истечении (от `versions.deprecated_at`, максимум по флитам проекта) deprecated → `disabled` — reconcile реапит её ready-буфер, живым матчам шлёт per-server `DrainServer{deadline_s=300}` (protocol.md §1; ровно один раз — сервер помечается `draining`), матчмейкер перестаёт её предлагать (старые клиенты получают `update_required`).
> - PrePull-таргеты — active-ноды с heartbeat <30с в регионах флитов проекта; нет живых нод → флип сразу (образам некуда греться). Repeated `POST /v1/deploy` идемпотентен (prepulling → отчёт о прогрессе, active → no-op); одновременно prepull'ится максимум одна версия проекта; `failed` PullReport абортит деплой сразу. Стейт ожидания prepull — in-memory, маркер — `versions.state=prepulling`: после рестарта master деплой резюмируется с новым 15-мин таймаутом (PrePull идемпотентен и дёшев на тёплом кэше).
> - `POST /v1/rollback {project?, region?}`: project можно опустить при единственном проекте; `region` ограничивает переключение `fleet_configs.active_version` этим регионом (состояния версий остаются глобальными); наружу — событие `deploy_rolled_back`.
> - События: `deploy_started`, `deploy_node_pulled`, `deploy_activated`, `deploy_failed`, `deploy_rolled_back`, `version_disabled`, `server_drain`. Метрики: `birdman_deploy_prepull_seconds` (histogram), `birdman_versions{project,env,state}`.
> - `PUT /v1/fleets/{region}` больше не сбрасывает `active_version` при отсутствии поля (nil → оставить как есть): владелец флипов — deploy-менеджер, прямое назначение осталось как bootstrap/ops-override.

## Окружения (environments v1)

> Миграция `000013_environments` + сиды в `ensureProject`. Окружение — **полноценное измерение** платформы, не лейбл: колонка `env` у versions/fleets/nodes/servers/matches, active-версия и окно deprecated скоупятся per (project, env). Прежний `versions.channel` (staging/prod) снят — он был **зрелостью билда, а не размещением**. Стейт-машина версий (§5) не изменилась — изменился только скоуп.

**Таблица `environments` (per-project) — флаги ведут политику, не имя:**

| Колонка | Смысл |
|---|---|
| `name` | имя (`^[a-z0-9][a-z0-9-]{0,31}$`, кроме `all`/`global`); иммутабельно |
| `production` (bool) | политика prod: авто-деплой запрещён, ретеншн-дефолт ∞, алерты critical |
| `auto_deploy` (bool) | регистрация версии сразу prepull→activate |
| `retention_keep` (int≥0) | сколько версий держать сверх окна; 0 = ∞ |

Сид каждому проекту: `dev` (production=false, auto_deploy=true, keep=20) + `prod` (production=true, auto_deploy=false, keep=0). **Guardrail-инвариант `auto_deploy=true ТОЛЬКО при production=false`** — CHECK в БД (`check (not (production and auto_deploy))`), валидация API и панель. FK-нарушения (нет такого env) в CreateVersion/UpsertFleet/CreateAPIKey мапятся в понятный `400 «no such environment <project>/<env>»`, не сырой 500.

**env как измерение (§1 DDL):**
- **versions:** unique (project, env, semver); `promoted_from` — provenance промоута; составной unique (id, project, env) — опора для FK флота.
- **fleet_configs:** PK (project, env, region); `active_version` обязан принадлежать тому же (project, env) — составной FK `fleet_active_version_env_fk` закрывает «dev-флоту prod-версию» на уровне БД.
- **nodes:** нода принадлежит ровно одному env; новые входят как `dev` (никогда prod неявно); перевод — явный `PATCH /v1/nodes/{id} {env}` (любой стейт кроме `dead`, без живых servers; иначе 409; событие `node_env_changed {from,to}`).
- **servers/matches:** денормализованный `env` строки исполнения — env ВСЕГДА из этой колонки, НИКОГДА join'ом к nodes (I6: перевод ноды не переписывает историю).
- **api_keys:** опциональная привязка `(project_id, env)` — строго парой (`check ((project_id is null) = (env is null))`); NULL/NULL = глобальный ключ (существующие работают как раньше).

**Удаление окружения (снимает прежний тупик «использованный env неудаляем», I10).** `DELETE /v1/environments/{project}/{name}` сносит окружение ВМЕСТЕ с содержимым — одной транзакцией, в порядке FK: `matches` → `servers` → `fleet_configs` (сначала `active_version = null`) → `versions` (у версий-потомков из других env обнуляется `promoted_from` — self-FK) → `match_stats_daily` → привязанные `api_keys` (**revoke**, не удаление: ключ отзывается и потому не может «стать глобальным»; привязку снимает FK `api_keys_env_fk`, утраченная пара сохраняется в событии `apikey_revoked {project, env, reason: environment_deleted}`) → строка `environments`. Событие `environment_deleted {project, name, production, versions, fleets, matches, servers, api_keys_revoked}` пишется в той же транзакции. **Ноды не каскадятся никогда:** предусловие — ноль нод в окружении (иначе 409), иначе живой агент остался бы с `node_id` в несуществующем env; побочно это гарантирует отсутствие живых серверов (guard перевода ноды их не пускает). Непустое окружение требует подтверждения — тело `{"confirm":"<name>"}` с ТОЧНЫМ именем (иначе 400); пустое (никогда не использованное) удаляется без confirm (204, как раньше).

**Стейт-машина per (project, env):** инвариант «одна active + одно окно deprecated» — per (project, env). `ActivateVersion` флипает строго внутри (project, env) — dev-флип не трогает prod-active; старшие deprecated → disabled. `DisableExpiredDeprecated` берёт `max(reap_ttl_min)` флотов **именно этого env** версии. Reconcile `PlanFleet` идёт по (project, env, region), **все шесть выборок серверов** скоупятся `s.env` (dev-проход не реапит prod-серверы того же региона); advisory-lock `project:env:region`. Deploy-менеджер: prepull-цели — active-ноды `env=version.env`; in-flight-ключ и busy-check — per (project, env); `HandlePullReport` матчит job по **(image_ref, нода ∈ pending)** — параллельные деплои одного ref в dev и prod (промоут!) не съедают отчёты друг друга.

**Промоут (`POST /v1/promote {version_id, to_env}`, scope deploy):** регистрирует версию в to_env (тот же project/semver/image_ref, `promoted_from`, state registered) + немедленный деплой; откат — существующий rollback. Идемпотентен: та же (project, to_env, semver) с **тем же** image_ref в registered → переиспользуется; с иным ref → 409. Привязанный ключ — только в свой env. **Поведение при занятом env:** если в (project, to_env) уже идёт деплой — промоут возвращает **409** (как у deploy), но версия УЖЕ зарегистрирована в to_env; после завершения текущего деплоя **повторите промоут** — он идемпотентно переиспользует registered-строку и запустит деплой. (Цепочка «только вперёд» — механизм auto_deploy-окружений; production-env авто-деплоя не имеет по guardrail'у — автоматического отложенного флипа прода не происходит, осознанно.)

**Авто-деплой — «только вперёд»:** мастер держит per (project, env) отметку `last_attempted` (created_at+id последней версии, которую пытался катить авто-деплой). Регистрация в auto_deploy-env: нет in-flight деплоя (project, env) → BeginDeploy сразу (+отметка); иначе версия ждёт registered. На **любом** завершении деплоя (activate из HandlePullReport, мгновенный activate при нуле живых нод, expire-таймаут, failed-report, abort) менеджер деплоит **новейшую registered строго новее `last_attempted`** (tie-break по id — CI-burst в одну секунду). Упавшая версия НЕ ретраится (вечный цикл битого образа исключён) — её вытеснит следующий билд либо ручной deploy. **Burst-грань:** событие `deploy_started` в авто-пути несёт `{"auto": true, "skipped": N}` — сколько промежуточных версий пропущено (при burst'е активируется только последняя). `Resume` при рестарте восстанавливает и in-flight, и цепочку (включая версию, зависшую prepulling без job'а после ошибки PrePullTargets).

**Ретеншн (`RetireVersions`, субтик реконсайл-лупа ~60с):** для env с `retention_keep>0` версии `registered|disabled` ранжируются по created_at desc; `registered` за позицией keep **и** старше 1ч → `disabled` (единственный путь registered→disabled; active/prepulling/deprecated не ранжируются и не трогаются; 1ч-защита от гонки с auto-deploy-очередью). Событие `version_retired {semver, env}`. Образ снятой версии снимается с нод окружения командой `RemoveImage` (`protocol.md` §1, `agent.md` §6), watermark-GC — страховка.

**Снятие образов — два такта (Фаза D 14.07.2026 показала, что одного мало).** (1) *Быстрый путь:* RemoveImage уходит немедленно при ЛЮБОМ переходе версии в `disabled` (флип-демоут, TTL, ретеншн) — fire-and-forget, без маркера. Но disabled-переход происходит ровно тогда, когда серверы этой версии ещё дренятся (grace 30с), поэтому агент типично отвечает `busy` («образ занят живым контейнером») и ничего не удаляет — повторить команду в старом дизайне было некому. (2) *Сходящийся sweep* (миграция `000015`, колонка `versions.image_cleanup_at`): тот же ~60с субтик выбирает версии, у которых `state='disabled'` **и** маркер пуст **и** **нет живых серверов версии** (`creating|ready|allocated|draining`) **и** образ не держит не-disabled версия того же (project, env) **и** в окружении нет `down`-ноды (batch-гигиена: окружение, заблокированное упавшей нодой, не выедает `limit 200` у здоровых; короткий офлайн до `node_down_after_min` держит HasSession-гейт) — и шлёт `RemoveImage` нодам окружения. Выборка ограничена `limit 200` — остаток доберётся следующим проходом.

> **Маркер — ПО ОТЧЁТАМ агента, а не по факту отправки.** Раньше sweep штамповал `image_cleanup_at` вслепую: протокол не нёс результата RemoveImage (`Ack` подтверждает лишь ПРИЁМ команды), поэтому пропущенное удаление — `busy` (образ под дренящимся контейнером) или `error` — терялось навсегда: версия выпадала из выборки, повторить было некому, образ доживал до watermark-GC. Теперь агент отвечает `ImageReport{removed|absent|busy|error}` (`protocol.md` §1), и маркер ставится, только когда **каждая** целевая нода окружения подтвердила, что образа у неё нет (`removed`|`absent` — равносильны). `busy`/`error` → маркера нет → версия остаётся в выборке → следующий субтик шлёт снова (дубль идемпотентен). Ожидания живут in-memory: рестарт мастера их теряет, но и маркера у версии нет, так что следующий субтик просто переотправит — сходимость по построению. Наблюдаемость: `birdman_image_removals_total{status}` (`ops.md` §1) — флот, где удаления стабильно возвращаются `busy`/`error`, теперь видно.
>
> **Офлайн-ноды: sweep не шлёт им НИЧЕГО.** Он повторитель (приходит к непомеченной версии каждые 60с), а команда офлайн-ноде лишь паркуется в in-memory очереди хаба — за сутки офлайна там копились бы тысячи дубликатов, вываливающихся на агента разом при реконнекте. Поэтому: нет живой сессии хоть у одной целевой ноды окружения → версия пропускается целиком (ни команды, ни маркера). Терять нечего — образ с офлайн-ноды всё равно не снять; вернётся нода — субтик отработает штатно. Не вернётся никогда — `dead` ставит ТОЛЬКО ручная ревокация (о пропаже кричит NodeDown-алерт); до неё долго-офлайн нода уходит в `down` (lease-checker после `node_down_after_min`), и её окружение выпадает уже из sweep-выборки (условие выше), а диск живых нод страхует watermark-GC. HasSession-гейт при этом остаётся боевым для короткого офлайна (сессия упала, `down` ещё не наступил) и как защита от гонки «выборка↔статус ноды». Быстрый путь остаётся fire-and-forget (одна отправка на disabled-переход, не повторитель) — его команда штатно доедет из очереди на реконнекте.

**Привязка ключей (enforcement, `requireScopeEnv`):** для скоупов deploy/matchmaking/allocate привязанный ключ обязан совпасть с (project, env) целевого ресурса (versions/deploy/promote/rollback — по env версии/цели; тикеты — project+env берутся/валидируются из привязки на создании **и сверяются с (project, env) самого тикета на чтении и отмене**, tracker #963; allocate — по env флота). Несовпадение → `403 {"detail":"key is bound to <project>/<env>"}` — **кроме чтения/отмены тикета: там `404` тем же телом, что и у несуществующего `ticket_id`** (403 назвал бы чужой тикет существующим, то есть раздал бы оракул по uuid); гейт стоит ДО rate-limit'а, который ключуется по `player_id` тикета, то есть по жертве. Привязанный ключ также **дефолтит project** (не только валидирует). NULL-привязка = глобальный ключ. Привязка несовместима со скоупом `admin` (400).

**BIRDMAN_ENV в дедике:** существующий map `StartServer.env` (`protocol.md` §1) несёт `BIRDMAN_ENV=<name>` — игровой сервер знает своё окружение (конфиги/аналитика). Ноль диффов proto/liba.

**Привязка ключа на чтении (tracker #974).** `GET /v1/matches/{id}` энфорсит привязку `(project, env)` ключа: привязанный ключ ЛЮБОГО скоупа (включая `readonly`) читает только матчи своей пары, чужой → `403 key is bound to <project>/<env>`. Исторически энфорсмент стоял лишь на deploy/matchmaking/allocate, и матч чужого проекта отдавался по uuid молча — при том, что листинг с #961 уже валидирует `?project=`. Глобальный ключ, как и раньше, видит всё; сессия панели — ровно то, что видит ключ, которым в неё вошли: `POST /v1/session` **не требует admin** (`requireScope` на нём нет) и наследует привязку ключа целиком, так что «сессия панели = admin» — удобная, но неверная посылка (см. #990 ниже). Матч теперь отдаёт своё окружение полем `env` (колонка была в схеме с environments v1, в API не выходила — без неё привязку не проверить).

**Сессия сообщает привязку ключа (tracker #1000).** `POST /v1/session` и `GET /v1/session` отдают `{"scopes":[…],"name":"…","binding":{"project":"…","env":"…"}}`, где `binding` присутствует **только у привязанного ключа** и отсутствует целиком у глобального/admin. Поле ADDITIVE: НАБОР полей для клиента, написанного до #1000, не изменился. Точности ради — байты изменились: тело собиралось `map[string]any` (ключи сортируются) и стало структурой (порядок полей), то есть `{"name":…,"scopes":…}` → `{"scopes":…,"name":…}`. Опереться на это некому: `/v1/session` в репозитории разбирает ОДНА панель (`panel/src/lib/api.ts`), в `sdk/`, `examples/`, `agent/`, `deploy/`, `infra/` вызывающих нет, а nginx панели ручку только маршрутизирует и rate-лимитит.

Форма — вложенный объект, хотя `GET/POST /v1/apikeys` ту же привязку кладёт ПЛОСКО (`project`/`env` с `omitempty` в теле ключа, `store.APIKey`). Это осознанное расхождение, и аргумент у него ровно один: `project` на верхнем уровне ответа сессии столкнулся бы по смыслу с «выбранным проектом» панели (мультипроект W2/W3, `?project=`), а `binding.project` ни с чем не путается. Аргумент «наличие одного поля = привязан» плоскую форму НЕ отличает — там `project?` с `omitempty` даёт то же самое. Заводишь третью ручку с привязкой — выбери одну из этих двух форм осознанно, а не по соседству.

Полупара (`project` задан, `env` — нет) недостижима при живом `CHECK api_keys_binding_all_or_nothing` и отвергается `CreateAPIKey`, но достижима по схеме; отдаётся как привязанный ключ с пустым `env`, а не как глобальный — `keyAllowed` такую пару не пропускает НИ НА ОДНОЙ ручке, где привязка вообще спрашивается, так что назвать её глобальной было бы хуже. Оговорка: «не пропускает никуда» относится к поверхности привязки (deploy + пять адресуемых чтений + тикеты); листинги и агрегаты привязку не энфорсят вовсе (см. «Границы» выше), и полупара читает их как любой readonly.

Зачем поле: сессия наследует ключ ЦЕЛИКОМ, поэтому привязка гейтит запросы панели (#974, #988, #990), а панель об этом не знала — и объясняла ЛЮБОЙ `403` единственным, что видела, скоупами, то есть говорила «нужен ключ со скоупом readonly или admin» привязанному readonly-ключу, у которого readonly есть. Честная диагностика отказа без этого поля невозможна в принципе; что панель с ним делает — `panel.md` §1 п.5. `DELETE /v1/session` тела не имеет и не тронут.

**Порядок проверок и оракул существования (tracker #989).** Ручек, энфорсящих привязку на чтении АДРЕСУЕМОГО объекта, четыре: `GET /v1/matches/{id}` (#974), `GET /v1/servers/{id}/logs` (#988), `GET /v1/environments/{project}/{name}/usage` (#989) и `GET`·`DELETE /v1/matchmaking/tickets/{id}` (#963). Тут два РАЗНЫХ решения, которые легко спутать в одно, — порядок проверок и код отказа; ниже они разведены.

**Порядок диктуется адресацией.** Пара `(project, env)` известна только ПОСЛЕ резолва объекта по непредсказуемому id (матч, сервер, тикет) → порядок вынужденный, «резолв → гейт»: гейту иначе нечего сравнивать. Пара — САМ АДРЕС ручки (usage окружения) → гейт стоит ПЕРВЫМ и в БД не ходит вовсе. **Правило:** гейт настолько рано, насколько позволяет адресация.

**Код отказа — решение отдельное, и по ручкам оно РАСХОДИТСЯ.** При раннем гейте оракула нет по построению: отказ формируется раньше, чем о существовании объекта что-либо известно, поэтому `403 key is bound to X/Y` приходит БАЙТ-В-БАЙТ одинаково на живое окружение, на выдуманное и на выдуманный проект (закреплено тестом `TestEnvironmentUsageEnforcesBinding` — сверяются ответы целиком, а не коды). При вынужденном позднем гейте существование объекта уже известно, и оракул зависит от выбора: `requireTicketBinding` (#963) намеренно отдаёт `404` тем же телом, что и честный промах, — оракула нет; `/v1/matches/{id}` и `/v1/servers/{id}/logs` отдают `403` на существующий чужой объект и `404` на несуществующий — оракул ЕСТЬ (замерено). То есть оракул #974/#988 — следствие выбранного кода, а не неизбежная плата за порядок. Расхождение здесь ЗАФИКСИРОВАНО, а не разрешено: у тикета неотличимость дёшева (uuid всё равно надо угадать, ответ и так пустой), а менять коды #974/#988 задним числом — ломать совместимость ради оракула, требующего знания uuid. Новая ручка выбирать не обязана: ранний гейт даёт неотличимость бесплатно, а `403` полезнее своему же оператору, промахнувшемуся окружением.

**Привязка ключа — АРЕНДАТОРСКАЯ ГРАНИЦА НА ЧТЕНИЯХ (решение владельца, tracker #993).** До #993 привязка была только поточечным гейтом над адресуемым объектом, а листинги её не энфорсили вовсе (`projectFilter`/`scopeFilter` слаг лишь ВАЛИДИРОВАЛИ), и привязанный readonly-ключ проекта Б читал через `?project=<чужой>` имена окружений, hostname и `public_ip` нод, `image_ref` версий, серверы, матчи, ленту событий и `/v1/stats/*` проекта А — а без параметра получал то же самое, потому что пустой фильтр значил «вся платформа». Теперь правило одно и у него ДВЕ половины, вторая не менее обязательная, чем первая:

1. явный ЧУЖОЙ `?project=` → `403 forbidden` `key is bound to <project>/<env>` — то же тело, что у `requireBinding`; чужой `?env=` — тоже `403`, но ТОЛЬКО на четырёх ручках, которые `?env=` реально читают (`/v1/nodes`, `/v1/versions`, `/v1/stats/*`): на остальных параметр как игнорировался, так и игнорируется, и `?env=prod` там неотличим от `?env=ghost` (оба `200`), потому что на выдачу не влияет ни тот, ни другой — env там берётся из привязки;
2. **ПУСТОЙ параметр сужает выдачу до пары `(project, env)` привязки** (по `env` — там, где у ресурса это измерение есть: у событий его нет, см. границу 4), а не до платформы. Без этой половины первая не значит ничего: дыра обходилась бы удалением параметра.

Совместимость для клиентов, читавших всю платформу привязанным ключом, сломана СОЗНАТЕЛЬНО — принятая цена решения. Глобальный и `admin`-ключ работают как раньше: привязку `admin` иметь не может (`CreateAPIKey` отвергает `admin`+binding), а панель по `panel.md` §1 п.5 логинится admin-ключом. Сессия панели при этом наследует привязку ключа логина ЦЕЛИКОМ (`POST /v1/session` не требует admin — см. #974 выше), поэтому оператор, вошедший ПРИВЯЗАННЫМ ключом, увидит в панели только свой проект и своё окружение: то же осознанное следствие, что и 403 на экранах «Логи»/«Метрики» после #990, а не отдельный дефект панели.

**Класс — ВЕСЬ, по роутеру:** `GET /v1/nodes`, `/v1/servers`, `/v1/versions`, `/v1/matches`, `/v1/environments`, `/v1/events`, `/v1/events/stream` (SSE, добавлен карточкой #999), `/v1/stats/overview`, `/v1/stats/cost` (общий вход — `httpapi.tenantScope`) плюс `GET /v1/projects`. Последний — ОСОБЫЙ и это надо знать: `?project=` он не принимает вовсе, поэтому `403` не отдаёт НИКОГДА, а сужение делает `keyBinding` уже ПОСЛЕ чтения из стора (`ListProjects` читает все строки, лишние отбрасывает Go-фильтр). То есть один и тот же ввод даёт `403` на восьми ручках и `200` на девятой; утечки нет (в теле только свой проект), но правило «гейт первым и в БД не ходит» — про `tenantScope`, а не про эту ручку.

**Порядок: в `tenantScope` для привязанного ключа гейт стоит ПЕРВЫМ и в БД не ходит ВООБЩЕ** — пара известна из самого ключа (правило «гейт настолько рано, насколько позволяет адресация», выше). Отсюда неотличимость, ради которой это и сделано так: `?project=game` (живой чужой) и `?project=zzz-nope` (выдуманный) дают БАЙТ-В-БАЙТ один ответ. Провалидируй мы слаг до гейта — код (400 против 403) сам стал бы оракулом существования, то есть дыра переехала бы, а не закрылась. Закреплено тестом `TestListingsRefuseForeignProjectForBoundKey` (сверяются ответы целиком, а не коды).

**Оракул `?env=` (#971) закрыт ЭТИМ ЖЕ гейтом, а не отдельной заплаткой.** Раньше `scopeFilter` валидировал `?env=` по паре и отвечал ЛЮБОМУ readonly-ключу `400 no such environment game/ghost`, то есть перечислял окружения чужих проектов; закрыть `?project=` и оставить это значило переселить оракул на второй параметр. Привязанный ключ теперь не доходит до `GetEnvironment`/`EnvironmentNameExists` ни на одном пути ЭТОГО КЛАССА, поэтому `?env=ghost` неотличим от `?env=<существующее чужое>` — и через границу проекта, и ВНУТРИ своего проекта (привязка — пара, поэтому чужой env своего проекта тоже `403`), и вовсе без `?project=`. Для НЕпривязанного ключа `?env=` остаётся валидируемым параметром с прежним `400`: он видит платформу по построению, оракулом это для него не является.

**`GET /v1/projects` тоже сужен, и это осознанный ответ на «раскрытие слагов принято» (#961).** Принято оно было ровно потому, что привязка тогда НЕ была границей на чтениях: перечислять слаги было не страшнее, чем читать по ним данные. Решение #993 эту посылку сняло, и оставить перечисление всех тенантов значило бы закрыть чтение данных, оставив открытым чтение состава платформы. Обоснование «400, а не 404, потому что `/v1/projects` и так перечисляет все слаги» (правило ниже) при этом цело: `400` достижим только для НЕпривязанного ключа, а он этот список и получает целиком.

**Границы решения, чтобы следующий не прочитал больше написанного.** (1) `/v1/alerts/*` закрыты СВОИМ правилом и отдельной картой (#995, подробности ниже в описании ручек): гейт на чужой `?project=` у них общий с этим классом (`tenantScope`), а ФИЛЬТР — свой, потому что не-скрывающий контракт `?project=` (#955) обязан уцелеть для непривязанного ключа. `GET /v1/alerts/rules` привязкой НЕ сужается — сознательно и по структурной причине (см. ниже). (2) `GET /v1/events/stream` (SSE) ЗАКРЫТ тем же гейтом (tracker #999) — до него фильтра там не было ВООБЩЕ, и сужение `/v1/events` обходилось подпиской на стрим; **это не «ещё одна ручка», а ВТОРОЙ ВХОД В ТУ ЖЕ ТАБЛИЦУ**, поэтому правила у них обязаны совпадать целиком, включая не-скрывающую половину. Специфика стрима — курсор: он ПОЗИЦИЯ, а не право, потому что скоуп берётся из ключа при ОТКРЫТИИ стрима и применяется к каждому опросу. Внутри соединения он БОЛЬШЕ НЕ заморожен навсегда (tracker #1016): учётка перепроверяется на каждом опросе, поэтому отзыв ключа, смена его скоупов или привязки закрывают уже открытую ленту в пределах периода опроса (~1с), а не «со следующего открытия». (3) Сырые проксии `/v1/logs/query`·`/v1/metrics/query*` закрыты привязанному ключу ДВЕРЬЮ (#990), сужение — #994. (4) У СОБЫТИЙ нет измерения `env` (колонка `events.project_id` есть с миграции `000019`, `env` — нет), поэтому привязанный ключ видит события своего проекта по ВСЕМ его окружениям; и фильтр ленты остаётся НЕ скрывающим — событие с `project_id is null` видно и привязанному ключу, как у алертов и у пика CCU (I5). **«Платформенное» тут значит ровно «`project_id is null`», а не «бекапы, CA и сессии панели»:** колонка объявлена `on delete set null` (миграция `000019`), поэтому после `DELETE /v1/projects/{slug}` ВСЯ лента удалённого тенанта — включая `image_ref` в payload'ах `deploy_started` — становится null-проектной и видимой каждому привязанному ключу. То же и с событием, которому бэкфилл не смог найти ссылку. Это следствие не-скрывающего правила, а не отдельный дефект, но полагаться на «null = безобидная платформенная служебка» нельзя. **Отдельно: `null` бывает не только «по существу», но и ПО ОШИБКЕ** — `apikey_revoked`/`apikey_purged` от `DELETE /v1/apikeys/{id}` уезжали платформенными не потому, что у ключа нет проекта, а потому что выборка стора не читала привязку, и имя чужого ключа (строка вида `ci-game-prod-deployer`) приезжало каждому арендатору и через `/v1/events`, и через SSE (tracker #1017, починено: обе выборки берут пару, payload всех трёх видов события собирается одним `apiKeyEventPayload`). Обратной силы у починки нет — строки, записанные раньше, остаются с `project_id is null`; нужен ли бэкфилл, решает человек. Проверены и остальные ручки, пишущие событие БЕЗ ссылок: `alert_muted`/`alert_unmuted` кладут `project` (и `null` там означает платформенный mute — по существу), `allocation_failed` кладёт, реестры и бекапы проекта не имеют вовсе. (5) Снимок `utilization` в `/v1/stats/cost` сужается ПРИВЯЗКОЙ, но не `?project=`/`?env=`: для глобального ключа он остаётся платформенным байт-в-байт, как и был. **И ПОДПИСЬ снимка следует за тем же фильтром (tracker #1009), а не за константой.** После #993 поле `utilization_note` осталось прежним текстом и стало противоречить собственным данным: привязанный ключ получал свои 7 слотов из 25 платформенных и тут же подпись «platform-wide … across ALL environments». Теперь оба — и выборка снимка, и его подпись — читают ОДИН `store.RegionUtilFilter`, поэтому разъехаться не могут; у непривязанного ключа строка прежняя байт-в-байт, у привязанного она называет его пару. Врало при этом ровно API: панель поле `utilization_note` не рендерит вовсе (тип в `panel/src/lib/api.ts` объявлен, но не читается), так что читателем был тот, кто ходит curl'ом или пишет свой клиент. (6) **`public_ip` активных нод остаётся публично доступным через `GET /v1/qos?project=&env=`** — ручка неаутентифицированная ПО ЗАМЫСЛУ (игровому клиенту нужны ping-таргеты), поэтому «привязанный ключ больше не видит чужие ноды» верно про `hostname`, `capacity_slots`, `state`, `labels`, cert-поля и сам факт принадлежности ноды окружению, но НЕ про IP: его отдаёт кому угодно та же платформа. Из этого же следует остаточный слабый оракул: `qos` непустого env с активными нодами отличается от `qos` выдуманного env наличием строк — гейт #993 на публичную ручку не распространяется и распространяться не может. (7) **`GET /metrics` по-прежнему не аутентифицирован**, и серии несут `{project, env, server_id}` — слаги проектов, имена окружений и состав флота достаются оттуда без ключа. Но с ЛИСТЕНЕРА API он ушёл (tracker #1003): экспозиция живёт на своём адресе (`listen_metrics`, деф. `127.0.0.1:9102`), а порт API отвечает там 404. Границей служит адрес, и это теперь свойство КОДА, проверяемое тестами `httpapi`, а не строка `location = /metrics` в конфиге прокси; тот, кто дотянулся до порта API, реестра не получает. (8) Правило «гейт раньше резолва» с tracker #1004 распространено и на WRITE-поверхность, где проект приезжает ПОЛЕМ ТЕЛА. Общий вход — `httpapi.bindProjectGate` (write-двойник `tenantScope`): он и дефолтит поле из привязки (CI одного проекта поле не шлёт), и энфорсит её — явный чужой слаг получает `403 key is bound to X/Y` НЕМЕДЛЕННО, до единого похода в стор, тем же `writeBindingDenied`, что на листингах. До этого в `POST /v1/rollback` привязка сверялась ПОСЛЕ `EnvsWithDeprecated`, и три состояния чужого проекта были различимы по ответу: `409` «нет deprecated-версии» (окон отката ноль), `409` «env is required» (больше одного), `403` (ровно одно). Гейт стоит на всех четырёх ручках этого класса — `/v1/rollback`, `POST /v1/versions`, `PUT /v1/fleets/{region}`, `POST /v1/matchmaking/tickets`. **Он закрывает ЧУЖОЙ ПРОЕКТ, а не пару целиком:** `env` резолвится ниже (у отката он вообще выводится из состояния БД), поэтому `requireBinding` на разрешённой паре остаётся обязательным, а внутри СВОЕГО проекта содержательные `409` сохраняются — свой тенант оракулом себе не является. Там, где проект не адресуется телом, а ВЫВОДИТСЯ из объекта (`POST /v1/deploy` и `/v1/promote` берут его из версии по uuid), гейт раньше стора невозможен по построению — остаётся поточечная проверка после резолва, как у `GET /v1/matches/{id}` (#974).

**Валидация `?project=` — ЕДИНОЕ правило API (tracker #961).** Слаг проекта, пришедший в `?project=` на **аутентифицированном чтении**, ВСЕГДА валидируется по БД: неизвестный → `400 {"error":"bad_request","detail":"no such project <slug>"}` (общий вход — `httpapi.validateProjectParam`, вызываемый из `httpapi.tenantScope`; прежнее имя `projectFilter` переименовано в #993 именно затем, чтобы безопасным по умолчанию входом стал ГЕЙТ, а «только валидация» была громким исключением — с #995 прямых вызывающих у неё не осталось ВОВСЕ: последние два, `/v1/alerts/active` и `/history`, переведены на `tenantScope`, а их не-скрывающий контракт уехал в ФИЛЬТР `httpapi.alertVisibility`). Пустой параметр = вся платформа для НЕпривязанного ключа; для привязанного он значит его пару (#993, «арендаторская граница» выше), и до валидации такой ключ не доходит — гейт отвечает `403` раньше. Правило заведено потому, что до него его не было: листинги W2 (`/v1/{nodes,servers,versions,matches}`) и алерты (#955) слаг не проверяли, `/v1/stats/*` (W3) проверял — API отвечал на один и тот же параметр двумя способами, и каждая следующая волна выбирала наугад. Больнее всего расхождение било по алертам: там пустой экран — ЖЕЛАННОЕ состояние, поэтому «алертов нет» и «я опечатался в проекте» выглядели одинаково и оба радовали. **400, а не 404:** сам ресурс (список/статистика) существует, плох ВВОД в query-параметре — тот же класс, что `?days=`/`?limit=`/`?state=`. Оракулом существования чужих сущностей ручка при этом не становится: 400 достижим только для НЕпривязанного ключа (привязанный получает `403` от гейта раньше — #993), а он readonly-скоупа и `GET /v1/projects` того же скоупа перечисляет ему все слаги. Панель опечатку послать не может по построению (`resolveProject` отдаёт только слаг из ответа `/v1/projects`, а удаления проектов в API нет вовсе) — 400 адресован человеку с curl'ом и скриптам. **Исключений ровно три, каждое по своей причине:** (1) `GET /v1/qos` — ручка ПУБЛИЧНАЯ, 400 «no such project» раздал бы оракул слагов кому угодно, аргумент «у вызывающего и так есть readonly» там не работает → resolve-or-empty; (2) `GET /v1/alerts/rules` — фильтр не принимает вовсе (каталог конфигурации); (3) `project` в ТЕЛЕ `POST /v1/alerts/mutes` — матчер хранимого правила, а не фильтр над данными (см. ниже). Добавляешь `?project=` на новую ручку — либо валидируй, либо впиши сюда четвёртое исключение с причиной. **`?env=` сведён к тому же правилу (tracker #971).** Общий вход — `httpapi.validateEnvParam` (вызывается из `tenantScope` на НЕпривязанном пути; до #993 это была вторая половина `scopeFilter`): при заданном `project` имя окружения проверяется В ЭТОМ проекте (пара, как у deploy/versions/promote), без проекта — достаточно существования имени хоть у одного проекта. Опечатка → `400 no such environment …` одинаково на `/v1/stats/*`, `/v1/nodes` и `/v1/versions`. До этого валидировала только статистика, а листинги молча отдавали пустой список — тот же класс, что был у `?project=` до #961. **Привязанный ключ сюда не попадает вовсе** (#993): для него та же валидация работала оракулом имён чужих окружений, поэтому он получает `403` до всякого похода в БД.

Аутентификация: `Authorization: Bearer <api-key>`; скоупы из таблицы `api_keys`. Скоуп `matchmaking` ограничен тремя ручками тикетов, но внутри них ограничен слабо: любой `player_id`, чтение и отмена любого тикета по `ticket_id` — владения тикетом нет вовсе (v0). Границей служит только привязка ключа к (project, env), и она проверяется на всех трёх ручках (tracker #963; до него — лишь на создании, `httpapi/matchmaking.go`): привязанный ключ работает только с тикетами своей пары, чужой отвечает `404` неотличимо от несуществующего. Глобальный (NULL/NULL) ключ, как и раньше, достаёт до всех проектов. Поэтому ключ рассчитан на **бэкенд игры**, а не на игровой клиент: вшить его в клиент = раздать общий секрет и потерять доверие к `player_id` (rate-limit — 5 rps per player_id, in-memory, это глушилка абьюза, не граница безопасности; per-IP лимита в master нет). Разбор границ — `architecture.md`, «Модель доверия (trust boundaries)».

(Уточнено в v0, панель П0.) **SSE `/v1/events/stream` реализован** (скоуп readonly+): новые строки `events` стримятся как `id:`/`event: <kind>`/`data: <json>` по курсору `events.id` (poll PG ~1с), keepalive-коммент каждые 15с, реконнект без потерь через `?after_id=` или `Last-Event-ID`. Выдача сужается арендаторской границей (см. выше): гейт `tenantScope` стоит ДО разбора курсора, сам фильтр уходит в SQL опроса, а курсор двигается по РАССМОТРЕННОМУ окну, а не по отданным строкам — иначе привязанный ключ, чей проект молчит, заставлял бы master каждую секунду сканировать хвост, накопленный соседним проектом. Экономия эта живёт ВНУТРИ соединения: на реконнекте клиент присылает свой последний ВИДИМЫЙ id, отставание возвращается целиком, и догон идёт по `sseBatchLimit` id за тик (~500/с — 2500 чужих событий между двумя своими дают около 6с тишины). Наружу при этом по-прежнему уходят только id видимых событий, так что `Last-Event-ID` клиента остаётся точным. **«Реконнект без потерь» и гонка коммитов (tracker #1013).** `events.id` выдаётся в момент INSERT'а, а события пишутся внутри транзакций, поэтому событие с МЕНЬШИМ id может стать видимым ПОЗЖЕ уже отданного: транзакция A взяла id 6 и держит коммит, B взяла 7 и закоммитилась — опрос видел 7, не видел 6, двигал курсор на 7, и событие 6 не приходило НИКОГДА. Теперь курсор перешагивает границу окна не раньше, чем через `sseSettle` (**5с**) ПОСЛЕ ТОГО, КАК ЕЁ УВИДЕЛ. Отсчёт именно от наблюдения, а не от `events.ts`: `ts` — это `now()`, то есть время НАЧАЛА транзакции, и о моменте, когда строка стала видимой, оно не говорит ничего. Из наблюдения же рассуждение прямое: если граница `hi` видна нам в момент T, любая строка с меньшим id вставлена ДО T, значит её транзакция была открыта уже в T. **Гарантия и её честная граница:** не теряется ничего, закоммиченное в пределах 5с после того, как более новое событие стало видимым; транзакция, висящая дольше, теряется по-прежнему (у master'а все пишущие транзакции — миллисекунды). Живой ленте это НЕ добавляет задержки: строки отдаются сразу, как только видны, ждёт только курсор; окно шириной в `sseSettle` перечитывается каждый опрос, а уже отданные id помнятся ПО СОЕДИНЕНИЮ (`sseSentCap` = 5000 — потолок памяти; пробившая его лента теряет защиту от гонки, но не память). **Остаточная граница, которую надо знать:** запоздавшее событие приезжает ПОСЛЕ более нового, поэтому `Last-Event-ID` у клиента может уйти назад — на реконнекте это даст ПОВТОР нескольких кадров, но не потерю; и защита живёт внутри соединения — переоткрывшись, клиент присылает свой последний видимый id, и события ниже него не вернутся. Дубликат вместо потери — сознательный размен: потерянное событие не отличимо от «ничего не было». **Отзыв ключа закрывает и уже открытый стрим (tracker #1016).** Учётка перепроверяется в цикле опроса — `authenticator.stillValid` сравнивает id, набор скоупов и привязку с теми, с которыми лента открыта; не сошлось или ключ больше не аутентифицируется — соединение закрывается, EventSource переоткрывает его и получает честный 401. Выбрана перепроверка, а не реестр открытых соединений: механизм инвалидации остаётся ОДИН (`invalidateKey` чистит кэш bcrypt и сессии, поэтому первый же опрос после отзыва идёт в БД и получает отказ), разделяемого состояния на горячем пути не заводится, а стоимость — поиск в мапе рядом с запросом к БД, который стрим делает и так. Лаг ограничен периодом опроса (~1с) против прежнего «бесконечно, пока клиент держит сокет»; у обычных ручек он по-прежнему ограничен `authCacheTTL`. Расширение прав закрывает ленту тоже — правило «соединение живёт ровно столько, сколько неизменна учётка, с которой оно открыто» проще и проверяемее, чем разбор направлений изменения, а клиент переоткрывает с `Last-Event-ID` без потери событий. **Продюсер SSE в master'е ровно один** — этот; маршрута `GET /v1/matchmaking/tickets/{id}/stream`, упомянутого в описании карточки, в коде нет. **`GET /v1/matches`** — read-model с join (semver, host, port, живые `server_players`), фильтры `state|region|project`, `limit/offset`, сортировка `created_at desc`; **`GET /v1/matches/{id}`**. **Сессии панели:** `POST /v1/session {api_key}` → HttpOnly Secure SameSite=Lax cookie (in-memory store, TTL 24ч, скоупы ключа), `GET /v1/session` → `{scopes,name,binding?}` (см. «Сессия сообщает привязку ключа» ниже), `DELETE /v1/session`; auth-middleware принимает Bearer ИЛИ cookie, для не-GET по cookie обязателен заголовок `X-Birdman-Csrf: 1`. **Панель встроена в бинарь** (`go:embed`, `internal/panelui`): `/` и `/assets/*` — статика с SPA-fallback, `/v1/*` без маршрута — JSON 404; без сборки панели бинарь отдаёт placeholder (сборка — `panel/build.sh`, детали в `master/README.md`).

- **`GET /v1/stats/overview?days=N`** (readonly, **N=1..30**, деф. 7 — потолок 30д = retention VM = горизонт роллапов; выше → 400) — агрегаты по дням (UTC, пустые периоды → нули, не пропуски; каждый ряд с единицей): `matches_per_day`/`players_per_day` (стек по региону; players = Σ`players_peak` — прокси), `peak_ccu_per_day` + `peak_ccu` (sweep-line пик одновременных `players_peak`), `avg_match_duration_seconds` (+ per-day), `version_distribution` (доли по semver), `time_to_match` p50/p95. **`GET /v1/stats/cost?days=N`** — `slot_hours_per_day_by_region`/`_by_version` (слото-часы = суммарное allocated-время дедиков из `matches [started_at,ended_at]`, разбито по UTC-дням) + `slot_hours_total` + `utilization` (снапшот allocated/ready/draining vs capacity active-нод по регионам). **Rollup-backed:** ответ = материализованные роллапы (`match_stats_daily` по дню×region×semver×env×**project** + `match_ccu_daily` по дню×**project**, где строка `project=''` — платформенный пик И маркер «день посчитан»; миграция 000017) за иммутабельные дни `[axis0..today-2]` + **живой пересчёт хвоста ≤2д** (сегодня/вчера из сырых `matches`, чтобы данные всегда свежие без ожидания джобы). Живой хвост предполагает, что матч «оседает» (завершается) в пределах этих ≤2 дней от старта — верно для сессионных dedik-матчей (минуты); матч, всё ещё идущий в момент, когда его день старта уходит из хвоста в иммутабельный диапазон роллапов, замораживает `avg_match_duration`/`players_peak` этого дня до следующего бэкфилла. Роллапы держит `statsrollup`-джоба (бэкфилл 30д на старте + тикер `stats_rollup_interval`, деф. 2м, пересчёт последних 2 UTC-дней). Датасет — только матчи, которые реально стартовали (`started_at is not null`). **Проектное измерение (мультипроект W3):** `?project=` сужает и роллапы, и живой хвост, включая пик CCU — проекты непересекающиеся тенанты, поэтому «пик под выбранным проектом» обязан быть пиком этого проекта (в отличие от env, где ёмкость флота общая и пик остаётся платформенным, I5). Пик НЕ аддитивен, поэтому проектные срезы считаются отдельным проходом, а не делением платформенного. Исторические строки, которые бэкфилл миграции не смог атрибутировать однозначно (один semver в двух проектах в один день), несут `project=''` и при заданном `?project=` ИСКЛЮЧАЮТСЯ: подмешивание засчитало бы одни матчи каждому тенанту. Последние 30 дней самолечатся — `statsrollup.Backfill` пересчитывает их из сырых матчей при каждом старте master. **Семантика занятости (occupancy, по спеке):** slot-hours и peak CCU считают **внутриоконную занятость** — долгий матч, начавшийся ДО окна, но идущий в нём, вносит свои слото-часы/игроков в дни окна (matches/players_peak/version_distribution по-прежнему по дню СТАРТА). `time_to_match` p50/p95 (перцентили неаддитивны → не в роллапе) читается узким запросом `matches.created_at→started_at` за окно; истинное «время в очереди» (ticket submit→matched) — гистограмма `birdman_mm_time_to_match_seconds` через metrics-proxy. Утилизация во времени — через metrics-proxy (`birdman_servers` / `birdman_node_capacity_slots`, `query_range`); в master — только снапшот.
- **`GET /v1/alerts/rules`** (readonly) → правила vmalert (имя, группа, severity, выражение, for, state, description), нормализованы из vmalert `GET /api/v1/rules` (recording-правила отфильтрованы). **`GET /v1/alerts/active`** → активные (state=firing) из vmalert `GET /api/v1/alerts`. **`GET /v1/alerts/history?limit=N`** → нормализованный список `{name,severity,region,node,startsAt,endsAt,description,active,received_at}` из лог-сина алертов (JSON-строки alertmanager-v2 `{received_at, alerts:[…]}`; битые строки пропускаются, поддержан и одиночный alert-объект в строке; `active` — по `endsAt`: пусто/zero/в будущем → true). В `/v1/alerts/active` и `/v1/alerts/history` каждому алерту добавлено поле `muted:bool` — есть ли активное mute-правило с совпадающим `alertname` И (region правила null ИЛИ == region алерта) И (project правила null ИЛИ == project алерта, **строго** — см. tracker #957 ниже). **Проектное измерение (мультипроект W2, tracker #955):** те же два ответа несут additive-поля `project` (лейбл алерта; пусто = платформенный) и `scope` (`"project"` при непустом `project`, иначе `"platform"` — выводится master'ом, чтобы панель не повторяла правило «пустой лейбл = платформенный»). Область определяется НАЛИЧИЕМ лейбла, отдельного лейбла `scope:` в правила vmalert не вводится — так корректно классифицируются и свои правила self-host-оператора (`ops.md` §1). Обе ручки принимают **`?project=`**, и фильтр **НЕ скрывающий**: алерт выпадает, только если его `project` ЯВНО не равен запрошенному, а алерт без лейбла остаётся видимым при любом выборе. Строгий фильтр отвергнут: у проекта нет режима «Все» (в отличие от `env`), поэтому он спрятал бы `MasterDown`/`NodeDown`/`DiskHigh` НАВСЕГДА — молча проглотить «мастер лежит» хуже, чем показать лишний алерт соседа (прецеденты — `keepForProject` ленты событий и платформенный срез пика CCU, решение I5/W3). В `/history` фильтр применяется ДО отсечения по `limit` — иначе `?limit=N&project=X` возвращал бы горстку записей, съеденных соседями. **Слаг ВАЛИДИРУЕТСЯ по БД (tracker #961)** — по общему правилу выше; «не скрывающий» и «валидируемый» — два разных вопроса, и на оба ответ «да»: опечатка больше не притворяется режимом «видны только платформенные», который на ЭТОМ экране неотличим от желанного «всё спокойно», а для существующего проекта платформенные алерты по-прежнему видны все. Проверка идёт ДО обращения к vmalert и ДО чтения лог-сина (опечатка не тратит апстрим и не превращается в 502/пустой список), но ПОСЛЕ `503 alerts_unconfigured`: «на этом мастере алертов нет вовсе» — факт более фундаментальный, чем плохой ввод. **`/v1/alerts/rules` не фильтруется вовсе:** это каталог конфигурации, а не инстансы алертов — у правила проекта нет, его `expr` разворачивается в серию на проект, и `project` живёт внутри текста запроса, а не в статических labels.

  **Привязка ключа на алертах — арендаторская граница, но со СВОИМ фильтром (tracker #995).** Замер карточки: привязанный readonly-ключ `neighbour/dev` получал `200` на `GET /v1/alerts/active` и видел горящий алерт чужого проекта `game` вместе со значением и описанием. Правило (решение владельца, продолжение #993): **привязанный ключ видит алерт, только если `project` алерта == его привязка ИЛИ пуст.** Вторая половина не менее обязательна, чем первая: платформенные `MasterDown`/`NodeDown` лейбла `project` не несут, и спрятать их значило бы не сказать арендатору, что лежит мастер, — гейт стал бы вреден. **Что стало с не-скрывающим `?project=`: он ЦЕЛ, но теперь обслуживает ровно НЕпривязанный ключ.** Переиспользовать его как гейт было нельзя — при пустом параметре он не фильтрует вовсе, поэтому граница обходилась бы удалением параметра; поэтому фильтров стало два и выбирает между ними `httpapi.alertVisibility` по признаку привязки, а не по непустоте слага (иначе будущее смягчение не-скрывающего фильтра молча смягчило бы и границу). Гейт «явный ЧУЖОЙ `?project=` → `403 key is bound to X/Y`» при этом берётся у общего `tenantScope` (#993), а не пишется в `alerts.go` заново: ответ на чужой слаг обязан быть тем же, что на листингах, включая неотличимость живого чужого проекта от выдуманного. **Граница на алертах — по ПРОЕКТУ, а не по паре `(project, env)`, и это надо знать:** ручка `?env=` не читает вовсе (поэтому и не гейтит его — гейтить параметр, не влияющий на выдачу, значило бы отвечать по-разному на запросы с одинаковым результатом), но лейбл `env` у части алертов ЕСТЬ — поэтому ключ, привязанный к `neighbour/dev`, видит алерты `neighbour/prod`. **Сколько именно правил его несут — ЗАМЕРЕНО, а не «правила агрегируют по (region, project, env)» вообще (tracker #1015):** сегодня их ТРИ из 19 (`rules.yml.j2`), и приходит `env` к ним ДВУМЯ разными путями. `BufferEmptyReadyProd` и `BufferEmptyReadyNonProd` агрегируют `sum by (region, project, env)` — лейбл в самом `expr`. `TickDegraded` его не агрегирует и в `expr` не упоминает вовсе, но с #1008 несёт: левая часть — пер-серверная серия агента `{server_id, project, env}`, а join сохраняет лейблы левой части (замерено на живой VictoriaMetrics v1.102.1 — на выходе `{env="prod", node, project, server_id}`). То есть перечень «правил с `env`» пополняется не только правкой правил, но и разметкой СЕРИЙ, на которых они стоят. **И ещё одно, чтобы цена не читалась шире, чем есть: сам лейбл `env` наружу НЕ выходит.** Нормализованный алерт (`alertEvent`) несёт `name`/`severity`/`region`/`node`/`project`/`scope`/`state`/`value`/`description`, поля `env` в нём нет — замерено на живом мастере: привязанный к `neighbour/dev` ключ получает алерт `BufferEmptyReadyProd` целиком, но об окружении узнаёт из ИМЕНИ правила и описания, а не из поля. Так что цена сужения-по-проекту — «сосед по СВОЕМУ проекту видит, что у тебя горит прод, и с каким значением», а не «читает имена твоих окружений» (оракул имён закрыт отдельно, #971/#993). Пар-точности листингов (#993, где чужой env своего проекта даёт `403`) у алертов НЕТ: решение владельца сформулировано по `project`, а «сузить до пары» — расширение решения (нужна вторая половина правила «`env` алерта == привязка ИЛИ пусто», иначе пропадут алерты без лейбла `env`), поэтому вынесено в отдельную карточку (tracker #1015), а не сделано молча. **Ещё один вход в ту развилку, замеренный там же: у mute'ов измерения `env` НЕТ вовсе** — таблица `alert_mutes` это `alertname`/`region`/`project`, а правило видимости у алертов и mute'ов ОДНО намеренно (`keepForBinding`, иначе арендатор увидел бы mute на невидимый ему алерт). Значит сужение алертов до пары не «добавляет вторую половину правила», а разводит две поверхности по разной точности: mute остаётся проектным (у него `env` пуст → «ИЛИ пусто» его сохранит), и dev-ключ будет видеть mute, поставленный на прод-алерт, которого он уже не видит. **Развилку закрыл владелец, и закрыл в пользу текущего поведения: граница на алертах остаётся по ПРОЕКТУ — это РЕШЕНИЕ, а не недоделанный хвост (tracker #1015).** Выбирали из трёх: оставить по проекту; сузить до пары, оставив mute'ы проектными (дёшево — фильтр и тесты, но сознательный рассинхрон «вижу mute, не вижу алерт»); сузить и завести `env` у mute'ов (консистентно, но это колонка + миграция + ручка + панель, отдельный эпик). Выбран первый: dev-ключ, не видящий, что горит прод его же проекта, — не очевидно лучшее поведение, чем нынешнее, а у оператора одного проекта интерес обычно ко всему проекту, а не к своей половине. Так что перечитывающему §6 не нужно заводить карточку на сужение заново — нужно знать цену, замеренную выше. Для непривязанного ключа (глобальный, `admin`, сессия панели, вошедшая таким ключом) не изменилось НИЧЕГО: `?project=` по-прежнему не скрывающий, опечатка по-прежнему `400`.

  **ОСТАТОЧНЫЙ КАНАЛ второй половины правила, названный вслух: платформенный алерт несёт `node`/`instance` — hostname КОНКРЕТНОЙ ноды, которая может принадлежать соседу.** `NodeDown`, `DiskHigh*`, `ContainerdDiskHigh*`, `CertExpiry`, `AgentlinkPendingStuck` лейбла `project` не несут (потому и видны привязанному ключу по решению владельца), но адрес узла в них есть. То есть «привязанный ключ больше не видит чужие ноды» после #993 верно про листинги и перестаёт быть верным целиком после #995: hostname чужой ноды достаётся из платформенного алерта. Спрятать нельзя — алерт без адреса узла бесполезен, а прятать сам алерт запрещает решение («иначе арендатор не узнает, что лежит мастер»). Это цена принятого правила, а не отдельный дефект, но считать периметр закрытым по hostname'ам нельзя. **И перечень выше — не весь остаточный канал: «платформенный» это ОТСУТСТВИЕ лейбла `project`, а не «алерт ничьего тенанта» (tracker #1020).** Отсутствие бывает ДВУХ происхождений, и цена у них разная. Структурное — правило безлейблово по построению (перечисленные выше); цена — hostname узла. ДЕГРАДИРОВАВШЕЕ — правило проектное по смыслу, но атрибуция не состоялась, и тогда наружу уходит вся полезная нагрузка ПРОЕКТНОГО алерта. Сегодня такое правило РОВНО ОДНО — `TickDegraded` (перебраны все правила `rules.yml.j2`: join'а нет больше ни у одного): проект ему доклеивается `on (server_id) group_left (project)` с `birdman_server_info`, а вторая ветка `unless on (server_id) birdman_server_info` намеренно оставляет алерт ГОРЕТЬ без лейбла, когда info-серии нет (master лёг, БД моргнула, дедика в БД ещё нет). Такой алерт уезжает КАЖДОМУ привязанному ключу вместе с `server_id` чужого дедика и его игровым тиком в `summary` — то есть цена здесь не hostname, а факт и величина деградации чужой игры. **Радиус после #1008 — меньше, но не ноль, и это ЗАМЕРЕНО**, а не выведено: реальное выражение правила прогнано на живой VictoriaMetrics v1.102.1 сразу по трём дедикам — с info-серией мастера → `project` есть; БЕЗ info-серии, но с парой от агента (дедик запущен после #1008) → `project` ЕСТЬ, то есть ветка `unless` для него уже не платформенная и деградация атрибутируется владельцу именно тогда, когда master ответить не может; без пары (дедик работал в момент апгрейда агента) → лейбла нет, остаются `server_id`, значение и `node`/`instance`. Остаток самоисчерпывается перекруткой таких дедиков — задним числом пара не дописывается (`agent.md` §9). **Подавлять эту ветку НЕ будем, и это решение, а не недосмотр:** она горит ровно тогда, когда master не может подтвердить владение, так что тушить её значит гасить алерт в момент, когда он нужнее всего, — то же самое возражение, которым обоснована сама вторая половина правила. - **Откуда берётся пара.** Она едет ВМЕСТЕ С ДЕДИКОМ, а не с хостом. Reconcile кладёт `BIRDMAN_PROJECT`/`BIRDMAN_ENV` в существующее map-поле `StartServer.env` (ноль диффов proto), агент пишет вывод дедика в путь `{log_dir}/servers/{project}/{env}/{server_id}.log`, а vector (`infra/roles/birdman_agent_dev/templates/vector.yaml.j2`) парсит пару из ПУТИ и вешает её стрим-лейблами рядом с `server_id`/`node`/`region`. Пока разметка не включена, привязанный ключ получает `200` с пустой выдачей: утечки нет, своих логов ещё нет.
- **Как сужается.** Master НЕ разбирает LogsQL/PromQL: парсер чужой грамматики на границе доступа — это своя пачка дыр (экранирование, пайпы, подзапросы). Вместо этого для привязанного ключа query-строка к апстриму СОБИРАЕТСЯ ЗАНОВО из белого списка (VL: `query`/`start`/`end`/`limit`; VM: `query`/`time`/`start`/`end`/`step`/`timeout`), и к ней добавляется фильтр master'а: `extra_stream_filters={project="…",env="…"}` для VictoriaLogs и `extra_label=project=…` + `extra_label=env=…` для VictoriaMetrics. Обе ручки выбраны именно потому, что их множественные значения складываются по **И** (проверено живьём): даже если клиентский параметр когда-нибудь протечёт мимо белого списка, он сможет только сузить сильнее, но не расширить. То есть НЕСУЩАЯ защита здесь — семантика самой ручки, а белый список второй слой: детерминизм плюс страховка от параметра, который у апстрима появится завтра и окажется не И-шным. Именно таков `extra_filters[]` у VM — брать его как НАШУ ручку **нельзя**: несколько `extra_filters[]` складываются по **ИЛИ** (проверено на живом VM v1.102.1: `{project="beta"}` рядом с `{project="alpha"}` возвращает серии обоих). В паре же с нашим `extra_label` клиентский `extra_filters[]` безвреден — он с ним просто пересекается. Запрос клиента при этом доезжает до апстрима ДОСЛОВНО — сужение не переписывает его текст.

Что VL/VM действительно чтят фильтр (включая запрос с чужим `server_id`, с пайпом `| sort by (_time) desc` и с пайпом `| union (…)`, которым можно попытаться подклеить второй запрос), доказывается интеграционно, на ЖИВЫХ апстримах: `TestLiveUpstream*` в `internal/httpapi`, включается `BIRDMAN_TEST_VL_URL`/`BIRDMAN_TEST_VM_URL` (без них — skip, поэтому CI-рецепт не меняется). Апгрейд апстрима — событие, требующее перепрогона этих тестов: ручка живёт не у нас. **Границы этого доказательства названы честно:** LogsQL — большой язык, и перебором пайпов «не пробивается ничем» не доказывается; опора здесь структурная — `extra_stream_filters` применяется VictoriaLogs на этапе ВЫБОРА СТРИМОВ, до того как отработают фильтры и пайпы самого запроса, и живой прогон это подтверждает на `| sort by (_time) desc`, `| union (…)` и `options(…) …`. Появится пайп, читающий данные в обход выбора стримов, — это регресс апстрима, и ловить его будет только интеграционный тест. **Отказ этого механизма был ТИХИМ И FAIL-OPEN — и закрыт канарейкой (следующий пункт, tracker #1007).** Апстрим, который ручку не знает (опечатка в имени параметра, VictoriaLogs/VictoriaMetrics старше ручки, Loki-совместимый эндпоинт вместо VictoriaLogs в `victorialogs_url` у self-host-оператора, прокси перед апстримом, срезающий query), просто ИГНОРИРУЕТ незнакомый query-параметр и отвечает `200` со всем флотом — замерено: `extra_stream_filterZ=…` → `200` и три строки из трёх, `extra_labelZ=…` → `200` и серии обоих проектов. При этом КРИВОЕ значение ЗНАКОМОЙ ручки честно отвергается: `extra_stream_filters={project=}` → `400 cannot parse value for tag "project"` у VL v1.51.0, `extra_label=project` → `422 must have the format name=value` у VM v1.102.1 (и на `/api/v1/query`, и на `/query_range`). Ровно на этой разнице — «незнакомое ИМЯ проглатывается, кривое ЗНАЧЕНИЕ знакомой ручки отвергается» — и стоит проверка. Требование к развёртыванию отсюда же: **минимальные версии — VictoriaLogs v1.51.0 и VictoriaMetrics v1.102.1** (те, на которых проверено; наши ansible-роли их и пинят), и `victorialogs_url` обязан указывать на VictoriaLogs, а не на Loki-совместимую замену.
- **Канарейка апстрима (tracker #1007): сужение больше не может молча НЕ сработать.** Перед тем как пропустить сужаемый запрос, master сверяется с пробой — разбирает ли апстрим ту ручку, на которой держится сужение (`internal/httpapi/narrow_probe.go`). Проба ДВУСТОРОННЯЯ: канареечный запрос с заведомо кривым значением ручки обязан дать `4xx`, а КОНТРОЛЬНЫЙ (тот же запрос без ручки) — `2xx`. Контроль здесь несущий, а не украшение: апстрим, отвечающий `4xx` на всё подряд (нужна авторизация, прокси не пускает), односторонней пробой прочёлся бы как «ручку понимает». Проба идёт по ТОМУ ЖЕ базовому URL и ТОМУ ЖЕ пути, что и боевой запрос, поэтому проверяется вся цепочка развёртывания, а не версия апстрима по документации: прокси, срезающий параметр, ловится ровно так же, как старая версия. Граница есть и тут: посредник, срезающий параметр ИЗБИРАТЕЛЬНО (по тексту запроса, по заголовку), пробу пройдёт — она доказывает маршрут, а не намерения того, кто на нём стоит. У метрик проверяются ОБА пути (`/api/v1/query` и `/query_range`) — ровно та поверхность, которую мы сужаем. Вердикт кешируется: 5 минут на «понимает» и 30 секунд на «не понимает»/«не проверить» (чтобы починивший апстрим оператор не ждал впустую). Вердикт старше TTL не используется — и вот что это значит буквально: если апстрим ПОДМЕНИЛИ под работающим master'ом на такой, что ручку не разбирает, то до конца TTL (максимум 5 минут) master продолжает сужать запросы «в пустоту», а подменённый апстрим отдаёт весь флот — дыра #990 открыта заново и молча. Это принятая цена ленивости: проба пересчитывается на первом запросе привязанного ключа ПОСЛЕ протухания, а не сама по таймеру, поэтому фонового мониторинга апстрима здесь нет и обещать его нельзя. Считается ЛЕНИВО, под одним мьютексом (всплеск запросов панели даёт один пробник) и ТОЛЬКО для привязанного ключа; глобальный/admin проходит мимо пробы и остаётся инструментом диагностики на сломанном развёртывании. На старте master прогревает обе пробы фоновой горутиной (`WarmNarrowProbes`) — сломанный апстрим виден в логе при загрузке, а не тогда, когда об него споткнётся первый привязанный ключ; НО прогрев не гейтит старт: наблюдаемость не имеет права ронять аллокацию. **Что при отказе:** ручка проглочена → `503` `logs_narrowing_unsupported` / `metrics_narrowing_unsupported` с текстом, называющим ручку, опцию конфига и минимальную версию; вердикта нет (проба не доехала, `5xx`, контроль не `2xx`) → `502 upstream`. Не `403` — у вызывающего есть право на эти данные, сломано РАЗВЁРТЫВАНИЕ, и `403` увёл бы оператора искать проблему в правах ключа. Тело ответа апстрима в отказ НЕ попадает (только код и наше объяснение): запрос пробы собран master'ом и парой привязки НЕ сужен, поэтому его отголоски привязанному ключу отдавать нельзя — иначе отказ сам стал бы каналом к тому, что закрывается. Тело уходит в лог master'а, где оно оператору и нужно. Пишется СМЕНА вердикта, а не каждая проба (иначе сломанный апстрим залил бы лог): отказ — `ERROR`, восстановление — `INFO`. Тексту `503` в панели соответствует своя строка каталога EN+RU (`metric.err.narrowing`, `panel.md` §1): без неё экран метрик показал бы общее «ошибка `metrics_narrowing_unsupported`», потому что прозу master'а панель в UI структурно не довозит. **Цена здоровому развёртыванию, названная точно:** не больше 2 запросов к VL и 4 к VM за 5 минут на весь master, и ровно ноль, пока привязанные ключи молчат. Но «ноль лишних запросов на боевом пути» сказать НЕЛЬЗЯ: фонового обновления вердикта нет, поэтому раз в 5 минут ОДИН пользовательский запрос оплачивает всю пробу синхронно, под мьютексом, и ждут её все, кто пришёл в это же окно. Ожидание ограничено сверху ОДНИМ бюджетом (`narrowProbeBudget`, 5 с на всю пробу целиком, а не на каждый её запрос) — то есть раз в 5 минут один запрос может стать на несколько секунд дольше. **Отсюда же новый узкий отказ, которого раньше не было:** апстрим, который отвечает, но МЕДЛЕННЕЕ бюджета пробы (боевой путь дал бы ему 15 с), привязанному ключу выдаст `502`, тогда как глобальный через тот же апстрим получит `200`. Бюджет оставлен коротким сознательно: запросы пробы тривиальны (`query=1` у VM — скалярная константа, индекс не трогается; `query=*&limit=1` у VL), 5 с для здорового апстрима — запас в три порядка, а платит за длинный бюджет живой пользовательский запрос. **Граница доказательства, названная честно:** канарейка доказывает, что ручка РАЗБИРАЕТСЯ, а не что она ЭНФОРСИТСЯ — апстрим, который параметр парсит, валидирует и семантически игнорирует, её пройдёт. Store-независимой пробы на энфорсмент не существует: «фильтр не вернул чужого» на пустом индексе неотличимо от «фильтр проигнорирован», а делать границу доступа зависящей от того, есть ли сейчас данные в индексе, нельзя. Энфорсмент доказывают `TestLiveUpstream*` на живых апстримах; саму канарейку — `TestNarrowingProbeGatesBoundKey` (фейковые апстримы четырёх повадок) и `TestLiveUpstreamNarrowingProbe`, где «апстрим не той версии» сделан из НАСТОЯЩЕГО VL/VM за прокси, срезающим ручку, с замером того, что тот же прокси отдаёт глобальному ключу весь флот.
- **Что становится с историей БЕЗ лейблов.** Строки, записанные в VictoriaLogs ДО разметки (а также логи дедиков, запущенных до выката, — они дописываются в старый плоский путь до конца жизни дедика, и логи run-once), пары не имеют и привязанному ключу **НЕ отдаются**: фильтр по паре их не выбирает. Это решение владельца по карточке #994: не «трактовать отсутствие лейбла как платформенное» (тогда дыра #990 осталась бы открытой ещё на всю ретенцию) и не «дропнуть» (логи флота не теряем — глобальный ключ видит их по-прежнему). Принятая цена: своя история глубиной до ретенции VictoriaLogs (14 дней, `ops.md` §1) привязанному оператору недоступна и деградирует сама по мере ротации.
- **Что привязанный ключ видит в метриках.** Только серии, несущие ОБЕ половины пары: `birdman_servers{project,env,…}`, `birdman_versions{project,env,…}`, `birdman_server_info{server_id,project,env}`. Серии с ПОЛОВИНОЙ пары ему тоже не видны — `birdman_events_total{kind,project}` и `birdman_allocation_failures_total{reason,project}` (нет `env`), `birdman_mm_queue_depth{region,env}` (нет `project`). Серии, у которых пары нет, для него не существуют — и это не мелочь, а названная граница. **Пер-серверные серии агента (`birdman_server_players`, `birdman_server_tick_ms`, `birdman_container_*`) пару НЕСУТ начиная с tracker #1008**: агент чеканит `(project, env)` в label'ы контейнера при create и поднимает их тем же `Restore` (`agent.md` §9), поэтому join через `birdman_server_info` из `ops.md` §1 остался у правил как страховка, а не как единственный источник проекта. **Граница здесь проходит теперь не по МЕТРИКЕ, а по ВОЗРАСТУ ДЕДИКА, и это главное, что надо знать:** задним числом лейбл не дописывается, так что у дедика, запущенного ДО апгрейда агента, серии остаются с одним `server_id` и привязанному ключу невидимы до перекрутки (старые доживают ретенцию VM). Замерено на живом стенде (VictoriaMetrics v1.102.1, master с привязанным readonly-ключом `alpha/dev`, ручка `/v1/metrics/query`): у дедика ПОСЛЕ апгрейда все четыре серии приходят целиком (`players=12`, `tick_ms=33`, `rate(cpu[3m])=0.37`, `mem=5000`); у дедика ДО апгрейда те же четыре запроса дают `200` и пусто, причём `seriesFetched: "0"` — `extra_label` не нашёл ни одной серии, а не отфильтровал найденную. Пар-точность на месте: пер-серверные серии соседнего проекта и СВОЕГО проекта из чужого окружения (`alpha/prod`) для этого ключа тоже пусты. Платформенные агрегаты (`birdman_players_online`, `birdman_matches_running`, `birdman_node_capacity_slots`) пары не имеют по существу — это данные всего флота, и привязанному ключу их видеть не положено. Практический итог для панели, замеренный тем же прогоном (на ручке, не в браузере — код панели этой картой не менялся): **четыре графика дедик-дровера и два графика матч-дровера у привязанной сессии РАБОТАЮТ** — но ровно для дедиков, запущенных после апгрейда, см. границу по возрасту выше (`panel.md` §65). На экране «Статистика» по-прежнему пусто, и это НЕ про агента: все четыре live-панели там платформенные, агентских серий на этом экране нет вовсе. `birdman_players_online` и `birdman_matches_running` лейблов не несут в принципе; `birdman_mm_queue_depth{region,env}` несёт половину пары (нет `project`); а утилизация пуста даже при целом числителе — знаменатель `sum(birdman_node_capacity_slots)` собран из серии с одним `{region}`, и пустой вектор в знаменателе обнуляет всё деление (`200` и пусто, а не `403`). Пятая VM-панель того же экрана — `sum by (state) (birdman_servers)` (`UtilizationChart`, он же на «Cost») — работает: замерено `{state="allocated"}=2`. **Join в правилах vmalert при этом НЕ менялся, ни строкой,** — вопреки опасению, записанному здесь до замера: `group_left (project)` не падает на левой части, уже несущей `project`, а ПЕРЕЗАПИСЫВАЕТ его значением из `birdman_server_info`, то есть авторитет владения остаётся за БД master'а (замер: агент чеканит `alpha`, БД говорит `dbsays` → на выходе `{env="dev", project="dbsays", server_id="s-new"}`; `env` при этом доезжает от агента — `group_left` его не перечисляет и не трогает). Цена апгрейда — только перекрутка дедиков, запущенных до него, и никакой правки правил.
- **Fail-closed.** Если пара привязки не проходит алфавит (ряд старше CHECK'а, будущее расширение алфавита), ручка отвечает `403 forbidden` `key is bound to <project>/<env>: scope is not narrowable, raw query proxy is global-key only` — то есть возвращается к двери #990, а не собирает фильтр «как получится». Разрешение по-прежнему проверяется ДО состояния проксии; но привязанный ключ теперь допущен, поэтому ненастроенный апстрим он видит как все (`503 logs_unconfigured`/`metrics_unconfigured`), а кривой `limit` — как `400`. Порядок проверок для привязанного ключа: пригодность пары (`403`) → настроен ли апстрим (`503 …_unconfigured`) → валидность `limit` (`400`, апстрима не касается) → канарейка апстрима (`503 …_narrowing_unsupported` / `502 upstream`) → сам запрос. Каждая ступень закрыта, а не открыта: ни одна из них не отвечает «отдам, раз проверить не смог».
- **Для self-host-оператора со своим шиппером.** Граница опирается на СТРИМ-поля `project`/`env` в VictoriaLogs. Шиппер, который кладёт пару в обычные поля события (или не кладёт вовсе), оставит своих операторов без их же логов — но не создаст утечки: фильтр по стрим-полям просто ничего не выберет. Класть пару в поле, которое может напечатать сам дедик, нельзя — тогда границу контролировал бы тот, от кого мы защищаемся.
- **Периметр этого сужения — только СЫРОЙ passthrough.** Курируемые чтения — отдельная история и отдельные карты: листинги и агрегаты привязку энфорсят с #993, алерты и mute'ы — с #995 (`GET /v1/alerts/rules` не сужен намеренно, там же и разобрано). Байтов игрового вывода среди них нет (он течёт ровно двумя путями — live-tail через агента и VL-проксия, оба закрыты), но считать периметр закрытым целиком нельзя.

## 7. Операционное

- Один бинарь `birdman-master`; конфиг `/etc/birdman/master.yaml` (dsn, listen :443 и :8443 gRPC, tls-серты, project defaults, `secrets_key_file`). systemd unit с `Restart=always`. (Уточнено в v0: дев-дефолты `listen_api :8100`, `listen_grpc :8444`; env-переопределения `BIRDMAN_DSN`/`BIRDMAN_LISTEN_API`/`BIRDMAN_LISTEN_GRPC`.) (Уточнено в v1, secrets-encryption §2.) `secrets_key_file` (деф. `/etc/birdman/secrets.key`, 0600, провижинится ролью `birdman_master_dev`) — мастер-ключ шифрования обратимых секретов at-rest (`registries.token`/`internal_ca.key_pem`), **обязателен**: без валидного ключа master не стартует (fail-loud). Env-оверрайды: `BIRDMAN_SECRETS_KEY_FILE` (путь, замещает yaml-значение) и `BIRDMAN_SECRETS_KEY` (значение base64 для dev/CI — при заданном значении оно **выигрывает** у файла; ровно один источник доходит до загрузчика ключа).
- (Уточнено в v1, mTLS agentlink.) Внутренняя CA живёт в Postgres (`internal_ca`, миграция 000008; master генерит её под advisory-lock при первом старте — ECDSA P-256, TTL 10 лет). Без внешних `tls.cert_file/key_file` master **выпускает себе server-лист от этой CA при старте** (в память, TTL 90 дней, hot-rotate за 14 дней до истечения через `GetCertificate`) — self-signed автоген (`EnsureServerCert`) выведен из эксплуатации. gRPC-листенер `:8444`: `ClientCAs` = активные CA, `ClientAuth: VerifyClientCertIfGiven` (Enroll обязан работать до выдачи серта); строгость Session — конфиг `agentlink_auth: token|mixed|mtls` (env `BIRDMAN_AGENTLINK_AUTH`, деф. `mixed`; `protocol.md` §Auth). Наблюдаемость: `birdman_agentlink_sessions{auth="mtls|token"}`, `birdman_tls_cert_expiry_timestamp_seconds{cert="ca|server"}`, `birdman_node_cert_expiry_timestamp_seconds{node}`, `birdman_agentlink_registries_withheld_total`.
- Graceful shutdown: стоп приёма API → дожидание in-flight (≤5с) → exit. Агенты переподключаются сами.
- QoS-эндпоинт: крошечный UDP-echo в составе агента на каждой тачке (порт 19999) — master отдаёт их список в `/v1/qos`.
- Логи master: journald, JSON-формат.

## 8. Acceptance

- **Ит. 1**: `curl /v1/allocate` <1с из warm pool; kill дедика → буфер восстановлен ≤10с; выключение тачки → карантин ≤15с, слоты пересозданы; crash-loop останавливает пересоздания.
- **Ит. 2**: два клиента получают один match {host,port} через тикеты; `update_required` для старого клиента; занятый дедик не выдаётся повторно.
- **Ит. 3**: deploy при живых матчах — 0 обрывов; rollback ≤1 мин; CI регистрирует версию и деплоит staging автоматически. *(истор.: «staging» здесь — ныне окружение `dev` с `auto_deploy`, §Окружения.)*
- **Ит. 5**: два региона, выбор по rtt из тикета; drain тачки — без обрывов.

# birdman self-host: от `git clone` до первого матча

English: [self-host.md](self-host.md)

End-to-end инструкция для **стороннего проекта**: поднять master, ввести первую
игровую ноду, выкатить версию билда и получить первый матч. Каждый сниппет
проверяем против кода веток self-host. Квикстарты, на которые опирается этот
документ: `deploy/README.md` (master), `infra/README.md` (ноды/ansible),
`master/README.md` (REST API + `mmcli`).

---

## 0. Что это и что нужно

birdman — лёгкий рантайм дедиков **без Kubernetes**: `master` (матчмейкер +
контроллер флота + REST + встроенная админ-панель), `agent` на игровых нодах
(поверх containerd) и SDK в самом дедике. Linux-only, session-based (одноразовые
матчи, не персистентные миры).

Топология self-host:

- **master-бокс** — один хост с Docker: master + Postgres (стек `deploy/`).
  Наружу торчит только gRPC-порт нод (`8444`, строгий mTLS); REST и панель
  слушают `127.0.0.1`.
- **игровые ноды** — по одной тачке на регион/ёмкость; вводятся с операторской
  машины через `infra/add-node.sh` (ansible). На ноде нужен Docker + containerd.

Требования:

- **master-бокс**: Docker + Docker Compose v2 (`docker compose version`), доступ
  наружу к порту `8444`, публичный IP.
- **операторская машина** (откуда вводишь ноды): `git`, `ansible-core`,
  `python3` + `PyYAML`, SSH-доступ к master-боксу и к нодам.
- **нода**: Docker + containerd, SSH-доступ, открытые наружу игровые порты.

> v1 self-host собирает master **из исходников** (`docker compose … --build`).
> Публичного образа пока нет — образ `birdman-master` вкомпилирует панель через
> `go:embed`, так что self-host получает продукт целиком (см. `master/Dockerfile`).

## 1. Master: поднять стек `deploy/`

Всё — из каталога `deploy/` клона репозитория:

```bash
git clone <repo-url> birdman && cd birdman/deploy

cp .env.example .env                                  # 1. задай POSTGRES_PASSWORD (не оставляй change-me)
umask 077 && openssl rand -base64 32 > secrets.key    # 2. ключ шифрования секретов at-rest
docker compose up -d --build                          # 3. собрать и запустить (postgres + master)
docker compose logs master | grep 'bootstrap admin'   # 4. admin-ключ (bmk_…) — показан ОДИН раз, сохрани
curl -s http://127.0.0.1:8100/healthz                 # 5. проверка: master отвечает (панель на том же адресе)
```

- **POSTGRES_PASSWORD** — без URL-спецсимволов (`/ @ # ? :`): пароль
  подставляется в `postgres://`-DSN как есть (`deploy/.env.example`).
- **admin-ключ** печатается один раз в лог старта (`bootstrap admin API key
  created — store it now, it is shown exactly once`, поле `api_key`); префикс
  `bmk_`, скоуп `admin`. Потеряешь — восстановление только через БД (деактивировать ключи в таблице api_keys → рестарт master ре-бутстрапит новый).
- **Панель + REST** — `http://127.0.0.1:8100`, вход в панель по этому же
  admin-ключу (или ключу со скоупом `readonly`). Порт опубликован **только на
  `127.0.0.1`** master-бокса.

**Наружу панель/REST — через reverse-proxy или SSH-туннель.** compose
публикует `8100` на `127.0.0.1` намеренно; чтобы открыть панель админу, поставь
перед ней reverse-proxy с TLS и аутентификацией, либо ходи туннелем:

```bash
ssh -L 8100:127.0.0.1:8100 <user>@<MASTER_PUB_IP>   # затем http://127.0.0.1:8100 у себя
```

### Панель по домену (опционально)

Если на master-боксе уже стоит nginx (раскладка Debian/Ubuntu с
`sites-available`) и уже выпущен сертификат на имя, роль `birdman_master_dev`
опубликует панель сама — задай две переменные инвентаря и прогони
`playbooks/dev-node.yml`:

```yaml
birdman_panel_domain: panel.example.com
# под wildcard-сертом это каталог БАЗОВОГО имени, а не хоста:
birdman_panel_tls_dir: /etc/letsencrypt/live/example.com
```

Пустой `birdman_panel_domain` (дефолт) означает, что роль не касается nginx
вовсе. Ни nginx, ни сертификаты роль не ставит: на боксе с чужими сайтами это
было бы вторжением — вместо этого она падает с подсказкой. Пишется ровно один
файл (`sites-available/birdman-panel` и симлинк на него), затем гоняется
`nginx -t`, и если тест не прошёл — симлинк снимается обратно: битый вхост не
доживёт до чужого reload.

Что делает сгенерированный вхост:

- терминирует TLS, редиректит `:80` → `:443`, проксирует всё на
  `127.0.0.1:8100` и передаёт `X-Forwarded-Proto` — именно от него master
  помечает сессионную куку флагом `Secure`;
- отдаёт **403 на `/metrics`** — теперь это лишь эшелон. С tracker #1003 master
  не отдаёт прометеевский реестр на порту API вовсе: реестр уехал на свой
  листенер (`listen_metrics`, деф. `127.0.0.1:9102`), а порт API отвечает там
  404. Аутентификации у экспозиции по-прежнему нет (скрейперу нечем носить
  ключ) — границей служит адрес. vmagent направляй на `127.0.0.1:9102`;
- лимитирует **`POST /v1/session`** (логин) — 10/мин с IP плюс общий потолок
  30 r/s, ответ `429`; `GET`/`DELETE` того же пути не считаются, поэтому
  проверка сессии панелью не душится;
- выключает буферизацию прокси и даёт SSE/live-tail логов таймаут чтения 1ч —
  реалтайм в панели продолжает капать.

Взвесь, что означает публичное имя: эндпоинт логина становится доступен всем, и
между ним и панелью стоит только admin-ключ. Держи ключ длинным либо поставь
дополнительный слой (VPN, allowlist по IP, identity-прокси). SSH-туннель выше
остаётся рабочей альтернативой.

**Два секрета self-host, оба git-ignored** (`deploy/.env`, `deploy/secrets.key`):

- `secrets.key` — ключ шифрования секретов в БД at-rest. Потеря = секреты в БД
  не расшифровать. **Эскроу-копию — в менеджер паролей** (`deploy/master.yaml`,
  runbook восстановления: `docs/specs/ops.md §5`).
- `.env` с паролем Postgres.

Конфиг master — `deploy/master.yaml` (без секретов; DSN приезжает env-переменной
`BIRDMAN_DSN` из compose). `agentlink_auth: mtls` включён с первого дня.

## 2. Первая нода: `infra/add-node.sh`

На **операторской машине** (тот же клон):

```bash
cd birdman/infra
cp inventories/dev/hosts.example.yml inventories/dev/hosts.local.yml
```

`hosts.local.yml` git-ignored — реальные IP/юзеры/ключи только в нём (конвенция
self-host: доступы вне git). Открой файл и в группе `birdman_dev` пропиши хост
`birdman-dev` = твой master-бокс (`ansible_host`, `ansible_user`,
`ansible_ssh_private_key_file`).

**Регистрация ноды идёт через master-бокс** (`delegate_to`): роль агента читает
admin-ключ из файла `/etc/birdman/master-admin.key` на master-боксе и дёргает
`POST /v1/nodes` на его же `127.0.0.1:8100`. Admin-ключ ноду не покидает. Значит
на master-боксе нужно **положить admin-ключ в файл** (стек `deploy/` его туда не
кладёт — он в логах compose):

```bash
# на master-боксе: вынь bmk_… из логов и сохрани 0600
cd birdman/deploy && docker compose logs master | grep 'bootstrap admin'
umask 077 && printf '%s' 'bmk_…' | sudo tee /etc/birdman/master-admin.key >/dev/null
sudo chmod 600 /etc/birdman/master-admin.key
```

Дальше — два пути ввода ноды.

### Путь A — прямой линк (рекомендуется для стека `deploy/`)

Стек `deploy/` не поднимает наш WireGuard-оверлей, поэтому агент ходит на
публичный `8444` master-бокса напрямую; публичный линк держит **строгий mTLS**
(не-loopback `master_addr` ⇒ конфиг-гейт агента требует mTLS). Отключи оверлей
на всём флоте — добавь в `hosts.local.yml` под `all: vars:` строку
`birdman_use_overlay: false` (тогда хаб-плей становится no-op) и убери у
`birdman-dev` строку `birdman_overlay_ip: 10.77.0.1`.

Введи ноду:

```bash
./add-node.sh node-eu-1 203.0.113.7 \
  --no-overlay --master-addr <MASTER_PUB_IP>:8444 \
  --region eu --user root --key ~/.ssh/id_ed25519
```

Что делает скрипт: валидирует ввод, дописывает host-блок в `hosts.local.yml`
(`birdman_use_overlay: false` + прямой `birdman_master_addr`), показывает diff,
после подтверждения прогоняет `ansible-playbook playbooks/add-node.yml`. Агент
поднимается демоном, регистрируется (`POST /v1/nodes` → одноразовый
`node_token`, 0600, только на ноде), тянет CA мастера (`GET /v1/ca`) и заходит
Enroll-by-token: обменивает `node_token` на клиентский mTLS-серт.

Полезные флаги (`./add-node.sh -h`): `--port` (SSH-порт), `--slots`
(дедиков на ноду, деф. 2), `--dry-run` (только напечатать блок, ничего не
менять), `-y/--yes` (без подтверждения записи).

```bash
./add-node.sh node-eu-1 203.0.113.7 --no-overlay --master-addr 203.0.113.1:8444 --dry-run
```

### Путь B — через наш оверлей (внутренний дефолт birdman)

Дефолт `add-node.sh` (без `--no-overlay`) назначает ноде overlay-IP
`10.77.0.X` (X≥2) и направляет control-plane на хаб `10.77.0.1:8444`. Этот путь
требует, чтобы на master-боксе **был поднят WireGuard-хаб** (изолированный
оверлей birdman, `10.77.0.0/24`, UDP `51827`) — его ставит ansible-роль
`birdman_overlay`, а не стек `deploy/`. Это конфигурация, в которой birdman
работает у себя (несколько нод за оверлеем). Детали хаба/сноса —
`infra/README.md` (раздел «Вторая+ нода»). Для свежего self-host на стеке
`deploy/` бери Путь A.

Проверка после ввода (в панели «Флот» или REST на master-боксе):

```bash
KEY=bmk_…   # admin-ключ
curl -s http://127.0.0.1:8100/v1/nodes -H "Authorization: Bearer $KEY"   # нода видна сразу (state=active)
```

## 3. Версия билда, флот и первый матч

Все REST-вызовы — с admin-ключом на master-боксе (`127.0.0.1:8100`) или через
туннель из §1. `KEY=bmk_…`.

```bash
# 1. зарегистрировать версию билда (образ игры). `env` (dev|prod|…) обязателен —
#    он заменил прежний `channel`; см. «Окружения» ниже.
curl -s -X POST http://127.0.0.1:8100/v1/versions -H "Authorization: Bearer $KEY" \
  -d '{"project":"game","semver":"1.0.0","image_ref":"ghcr.io/org/game:1.0.0","env":"dev"}'

# 2. включить warm pool региона (совпадает с --region ноды из §2)
curl -s -X PUT http://127.0.0.1:8100/v1/fleets/eu -H "Authorization: Bearer $KEY" \
  -d '{"project":"game","buffer_ready":2}'

# 3. мягкий деплой версии: prepull образа всем нодам → атомарный флип в active
curl -s -X POST http://127.0.0.1:8100/v1/deploy -H "Authorization: Bearer $KEY" \
  -d '{"version_id":"<version_id из шага 1>"}'
```

> Образ игры нода тянет по кредам реестра, которые master раздаёт нодам
> (`SetRegistries` по mTLS-линку; заводятся в панели, раздел «Реестры»).
> `add-node.sh` пишет ноде `birdman_registry_legacy: false` — токена реестра на
> ноде нет.

После флипа reconcile создаёт `buffer_ready` дедиков на ноде; дождись, пока
сервера станут `ready` (панель «Флот» или `GET /v1/servers`).

**Первый матч — `mmcli`** (второй бинарь, собирается `./master/build.sh` →
`master/dist/mmcli`; ключ со скоупом `matchmaking` или `admin`). `mmcli` заводит
тикет, long-poll'ит его и печатает `host:port` при матче.

⚠️ **Порядок флагов**: `--master`/`--key` — глобальные, идут **до** подкоманды
`request`; `--player`/`--version`/`--region`/`--measure`/`--project`/`--timeout`
— **после** `request`.

```bash
# rtt регионов задаёшь вручную (NAME:RTT_MS, повторяемо):
mmcli --master http://127.0.0.1:8100 --key $KEY request \
  --player p1 --version 1.0.0 --region eu:5
# → JSON результата + строка "203.0.113.7:20001" при матче
```

Либо дать `mmcli` **измерить** rtt самому — UDP-пробы по `GET /v1/qos`
(приёмочный замер; в проде rtt меряет клиент игры). С `--measure` регион можно
не задавать:

```bash
mmcli --master http://127.0.0.1:8100 --key $KEY request \
  --player p1 --version 1.0.0 --measure
# опционально: --probes 5 --probe-timeout 700ms
```

Exit-коды `mmcli`: `0` — matched, `1` — иной терминальный статус/ошибка, `2` —
usage. Два `mmcli request` с разными `--player` в одном регионе получают один
`host:port` и `match_id` — это и есть первый матч.

Прямая аллокация без матчмейкера (для интеграции своего бэкенда) —
`POST /v1/allocate {project,region,match_id}` (идемпотентно по `match_id`,
`409 no_capacity` при отсутствии ёмкости). Полный REST — `master/README.md`.

### Окружения: dev, prod, промоут

У каждого проекта есть **окружения** — как минимум `dev` (поток билдов из CI) и
`prod` (то, во что матчатся реальные игроки). Это полноценное измерение, а не
лейбл: версии, флоты, ноды, серверы и матчи принадлежат одному `(project, env)`,
active-версия скоупится по окружению — dev-билд физически не может флипнуть то, во
что играет прод. Поэтому `POST /v1/versions` (шаг 1 выше) принимает `env`
(dev|prod), а не прежний `channel`.

Поведение ведут два per-env флага, не имя:

- **`auto_deploy`** (деф. у dev): регистрация версии сразу prepull'ит и активирует
  её — каждый пуш CI выкатывается в dev без лишних вызовов. При burst'е деплоится
  только новейшая («только вперёд»); упавший билд не ретраится, его вытесняет
  следующий пуш. Несовместим с `production` (guardrail в БД и API).
- **`production`** (деф. у prod): авто-деплой запрещён, ретеншн хранит версии
  бессрочно, алерты critical.

**Промоут dev → prod** — одно действие: регистрирует *тот же image_ref* в целевом
окружении (provenance `promoted_from`) и деплоит:

```bash
curl -s -X POST http://127.0.0.1:8100/v1/promote -H "Authorization: Bearer $KEY" \
  -d '{"version_id":"<dev-версия>","to_env":"prod"}'
```

Идемпотентен (повторный промоут того же ref переиспользует registered-строку).
Если в prod уже идёт деплой — промоут вернёт `409`, но версия уже зарегистрирована
в целевом окружении; когда текущий деплой завершится — повторите промоут
(идемпотентно переиспользует registered-строку и запустит деплой).

**Нода принадлежит одному окружению.** Новые ноды входят как `dev` (никогда prod
неявно); перевод пустой ноды — явный (любой стейт, кроме `dead`, без живых
серверов на ней):

```bash
curl -s -X PATCH http://127.0.0.1:8100/v1/nodes/<node_id> -H "Authorization: Bearer $KEY" \
  -d '{"env":"prod"}'
```

**Ключи можно привязать** к паре `(project, env)` (`POST /v1/apikeys {project,
env}`) — привязанный deploy-ключ работает только в своём окружении (dev-ключ на
prod-деплой → 403). Оба поля пустые = глобальный ключ (дефолт; существующие ключи
работают как раньше). CI держит два: dev-привязанный на каждый пуш (авто-деплой) и
prod-привязанный под approval GitHub environment для промоута.

**Привязка — это граница арендатора, а не только гейт на запись.** Она сужает и
ЧТЕНИЯ, но НЕ везде с одинаковой гранулярностью, и разница важна:

- **по паре (project, env)** — листинги и агрегаты (явный чужой `?project=` →
  `403`, без параметра — сужение до своей пары) и сырые проксии наблюдаемости;
- **только по ПРОЕКТУ** — лента событий и её живой SSE-стрим, активные алерты и
  mute'ы. Ключ, привязанный к `game/dev`, видит события и алерты `game/prod`
  тоже: разделения по окружениям на этих поверхностях нет.

**Два фильтра различаются ещё в одном, и вот это как раз удивляет операторов.**
Второй — **не скрывающий**: строка без проекта — платформенное событие, алерт
`MasterDown`/`NodeDown` — остаётся видна любому привязанному ключу, иначе
арендатор молча не узнал бы, что лежит платформа. Первый — сырые проксии
наблюдаемости — **скрывает**: строку лога или серию метрик, которая пары не
несёт, привязанный ключ не получает вовсе. Замерено на VictoriaLogs v1.51.0 /
VictoriaMetrics v1.102.1: нелейблованная легаси-строка лога и серия
`birdman_players_online` (у неё нет лейблов вовсе) глобальному ключу отдаются,
привязанному — нет. Это та же ловушка, что `log_scope_dirs` ниже, — разбор в
разделе 4 «Кто что видит».

Чего привязка не закрывает вовсе: `GET /metrics` не аутентифицирован и несёт
`{project, env, server_id}` (слаги проектов, имена окружений и состав флота
достаются вообще без ключа), а `GET /v1/qos` публична по замыслу и отдаёт
адреса активных нод. С порта API реестр, впрочем, больше не достаётся: с
tracker #1003 он отдаётся на отдельном листенере `listen_metrics` (деф.
`127.0.0.1:9102`), то есть тот, кто дотянулся до порта API, его не получает, и
гарантия больше не зависит от конфига твоего прокси. Держи этот листенер на
loopback (или выключи ручку совсем — `listen_metrics: ""`, если скрейпера нет) и
не проксируй `/metrics` наружу.

Две вещи, которые лучше знать ДО того, как раздать привязанные ключи:

- клиент, который читал всю платформу привязанным ключом, сломан сознательно;
- **у наблюдаемости своя цена, и она не сводится к «видно меньше»** — часть
  своих же логов привязанный ключ не увидит вовсе. Разбор — раздел 4 «Кто что
  видит»; прочти его перед тем, как выдать оператору привязанный ключ.

Открытым оставлен `GET /v1/alerts/rules`: это каталог конфигурации, а не
инстансы срабатываний, и без него арендатор не может объяснить себе свои же
алерты. Цена — `state` и `expr` чужих правил видны; не хардкодь слаг проекта
в выражения правил.

**Ретеншн** (`retention_keep` на окружении, деф. dev=20, prod=0=∞): версии сверх
новейших N уходят в `disabled`, их образы снимаются с нод окружения. Снятие идёт
в два такта: `RemoveImage` уходит сразу при переходе в `disabled`, но контейнеры
версии в этот момент обычно ещё дренятся (агент честно пропускает занятый образ) —
поэтому **сходящийся sweep** того же ~60с субтика переотправляет команду, когда живых
серверов версии не осталось. Агент докладывает РЕЗУЛЬТАТ каждого снятия (`removed`,
`absent`, `busy`, `error`), и мастер штампует `versions.image_cleanup_at` («готово,
больше не шлём») только когда КАЖДАЯ целевая нода окружения подтвердила, что образа у
неё нет; `busy`/`error` оставляют версию непомеченной — следующий sweep просто повторит.
Ноде, которая сейчас офлайн, sweep не шлёт ничего (иначе в in-memory очереди копились бы
дубликаты). Смотрите `birdman_image_removals_total{status}`: флот, застрявший на
busy/error, течёт по диску. Watermark-GC диска остаётся страховкой.
`active`/`prepulling`/`deprecated` не трогаются никогда — окно отката остаётся тёплым.

Управление окружениями — в панели **Админка → Окружения**, либо через
`GET/POST /v1/environments` и `PATCH /v1/environments/{project}/{name}`.
Удаление окружения сносит и всё его содержимое (версии, флоты, матчи, серверы;
привязанные ключи отзываются), поэтому просит подтверждение — ввод имени
окружения; и отказывает, пока в нём есть тачки: сначала переведите их в другое
окружение (Флот → *Перевести в env…*, либо `PATCH /v1/nodes/{id}`).

## 4. Наблюдаемость (опционально)

Панель показывает графики/логи, если указать URL **своих** VictoriaMetrics /
VictoriaLogs. Раскомментируй в `deploy/master.yaml`:

```yaml
metrics:
  victoriametrics_url: "http://127.0.0.1:8428"
  victorialogs_url: "http://127.0.0.1:9428"
```

**Оставить блок закомментированным — это НЕ «пусто».** Собственный дефолт
мастера для этих двух ключей — ровно те URL, что напечатаны выше
(`http://127.0.0.1:8428` и `:9428`), и он подставляется ДО разбора YAML, так что
отсутствующая секция `metrics:` его не обнуляет. Следствия — замерены прогоном
`deploy/master.yaml` вербатим на мастере, у которого на этих портах никто не
слушает:

- на боксе случился референс-стек → вкладки просто работают, настраивал ты их
  или нет;
- там никого нет → все три ручки отвечают **`502 upstream`**, а не `503`. Панель
  эти два кода различает (`503` рисуется как «не настроено», `502` — как
  «недоступно»), то есть это разница между «иди чинить конфиг» и «иди чинить
  стек, который ты не разворачивал». Мастер при этом пишет в лог старта
  `ERROR upstream narrowing probe failed` по обоим апстримам;
- нужно честное «не настроено» → раскомментируй блок и поставь **ЯВНУЮ пустую
  строку**: `victoriametrics_url: ""`. Только она даёт
  `503 metrics_unconfigured` / `logs_unconfigured`.

`503 *_unconfigured` — один из ТРЁХ ответов со стороны апстрима, и значат они
разное: не настроено (`503 *_unconfigured`), апстрим не умеет сужать
(`503 *_narrowing_unsupported`, только привязанному ключу, tracker #1007),
апстрим не отвечает (`502 upstream`). Сверх этого привязанный ключ получает
`200` с суженной (иногда пустой) выдачей, кривой `limit` у logs-проксии — `400`,
а `403` приходит либо по скоупу ключа, либо на непригодной к сужению паре — сама
по себе привязка эти ручки НЕ закрывает. Точный порядок, в каком мастер это
проверяет, — в конце раздела, «В каком порядке отвечает master».

**Кто что видит (tracker #994).** Глобальный (непривязанный) ключ ходит в обе
сырые проксии — `GET /v1/logs/query` и `GET /v1/metrics/query`·`/query_range` —
как раньше: парой его запрос не сужается. Но «как есть» верно только для двух
metrics-ручек: у logs-проксии `limit` мастер ставит и клампит ВСЕМ (см. конец
раздела). Ключ, **привязанный к паре
(project, env)**, получает `200`, но master СУЖАЕТ его запрос этой парой
(`extra_stream_filters` у VictoriaLogs, `extra_label` у VictoriaMetrics), так
что чужих строк и чужих серий он не получает ни при каком запросе. Следствия,
о которых важно знать заранее:

- **Логи без пары привязанному ключу не отдаются.** Пара едет в стрим-лейблы
  `project`/`env` из ПУТИ файла лога (`{log_dir}/servers/{project}/{env}/{id}.log`,
  `docs/specs/agent.md` §5). Значит НЕ размечены: всё, что записано в
  VictoriaLogs до обновления; логи дедиков, которые уже работали в момент
  обновления (они дописываются в старый плоский путь до конца жизни дедика);
  логи run-once. Такие строки видит глобальный ключ и не видит привязанный —
  они доживают ретенцию VictoriaLogs (у референс-стека 14 дней) и исчезают
  сами. Это осознанный размен: альтернатива «считать строку без пары
  платформенной» вернула бы чтение чужого игрового вывода на всю глубину
  ретенции.
- **Разметку включает нода, и САМА она не включится.** Агент кладёт лог в путь
  с парой только при `log_scope_dirs: true` в его конфиге (`agent.yaml`), а
  **дефолт самого бинаря агента — `false`**. Порядок не случаен: бинарь агента
  обновляется сам (`POST /v1/agent-upgrade`), конфиг шиппера — нет, и агент,
  начавший писать в подкаталоги раньше своего vector'а, перестал бы отправлять
  логи вообще (старый glob `servers/*.log` новый путь не матчит). Поэтому флаг
  и новый конфиг vector'а кладёт ОДНА и та же ansible-роль `birdman_agent_dev`
  (переменная `birdman_log_scope_dirs`, деф. `true` — это дефолт РОЛИ, не
  бинаря), а голый апгрейд бинаря оставляет старую безопасную раскладку.

  **Ловушка: пока флаг выключен, привязанный ключ получает `200` с ПУСТОЙ
  выдачей** — не `403`, не `502`, вообще не ошибку. На экране это неотличимо
  от честного «за этот период логов нет», и ждать сигнала не от чего: ни
  master, ни панель про выключенный на ноде флаг не знают. Само по себе
  обновление мастера сюда не доезжает — прокати свой config management по
  ИГРОВЫМ НОДАМ (у нас это `cd infra && ansible-playbook playbooks/add-node.yml`:
  роль `birdman_agent_dev` едет на группу `birdman_nodes`; `dev-node.yml` — про
  мастер-бокс, ноды он не трогает).

  Проверка, отвечающая прямо, — посмотреть флаг на самой ноде:
  `grep log_scope_dirs /etc/birdman/agent.yaml`. Косвенная, если на ноду не
  попасть: сравни выдачу по ОДНОМУ дедику, про который точно знаешь и проект,
  И ОКРУЖЕНИЕ (то есть ровно свою пару), — сходи за его `server_id` сперва
  глобальным ключом, потом привязанным. Видит глобальный и не видит
  привязанный → дело в разметке. Само по себе «привязанный получает пусто»
  не доказывает ничего: так же выглядит и честное «за это окно логов нет», и
  корректно сработавшая граница на дедике из ЧУЖОЙ пары (в том числе из
  другого окружения того же проекта). Обратный исход — «оба видят одно и то
  же» — тоже не повод расслабиться: ровно так выглядит fail-open апстрима из
  следующего пункта, поэтому сверять надо не «непусто ли», а что выдача
  привязанного строго ВЛОЖЕНА в выдачу глобального.
- **Версии апстримов — не косметика, и master теперь проверяет, что апстрим
  ручку сужения действительно РАЗБИРАЕТ (tracker #1007).** Сужение опирается на штатные ручки `extra_stream_filters`
  (VictoriaLogs) и `extra_label` (VictoriaMetrics), и исполняет его АПСТРИМ, а
  не master. Апстрим, который такой ручки НЕ знает, ошибкой не отвечает — HTTP
  молча игнорирует незнакомый query-параметр, то есть апстрим отдал бы `200` со
  всем флотом. Поэтому перед тем как пропустить запрос привязанного ключа,
  master проверяет апстрим пробой: канареечный запрос с заведомо КРИВЫМ
  значением ручки обязан быть отвергнут (`4xx`), а контрольный, без ручки, —
  сработать (`2xx`). Оба выполнены → ручка разбирается, и master пропускает
  суженный запрос. Не выполнены — **master ОТКАЗЫВАЕТ, а не отдаёт данные
  всех**:

  - `503` + `logs_narrowing_unsupported` / `metrics_narrowing_unsupported` —
    апстрим проглотил значение, которое разобрать невозможно, значит он не
    разбирает ручку вовсе. В тексте ошибки названы ручка, опция конфига и
    минимальная версия. Чинить надо апстрим, а не ключ.
  - `502` + `upstream` — проба не дошла до вердикта (апстрим лежит, отвечает
    `5xx`, перед ним шлюз, который не пускает никого, **или апстрим отвечает,
    но медленнее 5-секундного бюджета пробы** — боевому запросу дали бы 15 с,
    поэтому очень медленный, но живой апстрим может обслуживать глобальный ключ
    и отказывать привязанному). Отказ здесь тоже намеренный: «не смог
    проверить» — это не «проверил».

  Тела ответа апстрима ни в одном из отказов нет — только его код и наше
  объяснение. Запрос пробы master составляет сам, и парой привязки он НЕ сужен,
  поэтому пересказывать привязанному ключу то, что проба получила, нельзя: отказ
  сам стал бы каналом к тому, что мы закрываем. Тело уходит в лог master'а — там
  оно тебе и нужно.

  Проба идёт по тому же URL и тем же путям, что и боевой запрос, поэтому
  проверяет всю твою цепочку целиком: старая версия, Loki-совместимая замена в
  `victorialogs_url` и обратный прокси, срезающий query-параметры, проваливают
  её одинаково. Она выполняется на старте master'а (ошибку видно в логе при
  загрузке, а не тогда, когда об неё споткнётся первый привязанный ключ; при
  этом провал пробы НЕ мешает master'у стартовать) и потом кешируется на 5
  минут — здоровое развёртывание платит не больше 2 запросов к VictoriaLogs и 4 к
  VictoriaMetrics за 5 минут — и ровно ноль, пока привязанные ключи молчат.
  Фонового обновления вердикта НЕТ, поэтому раз в 5 минут ОДИН пользовательский
  запрос оплачивает всю пробу синхронно и может занять на несколько секунд
  дольше обычного. Вердикт старше 5 минут не используется — и понимать это надо
  буквально: подменишь апстрим под работающим master'ом на такой, что ручку не
  разбирает, — и до конца этого срока (до 5 минут) master будет сужать «в
  пустоту», а подменённый апстрим отдавать весь флот. Это НЕ мониторинг: проба
  ленивая, она пересчитается на первом запросе привязанного ключа ПОСЛЕ
  протухания, а не сама по таймеру. Избирательное вмешательство — тоже её слепое пятно:
  посредник, срезающий параметр не всегда, а по тексту запроса или по заголовку,
  пробу пройдёт — она доказывает маршрут, а не намерения того, кто на нём стоит.
  **Глобальный (непривязанный) ключ пробой не гейтится** — сужать его нечем, так
  что он остаётся твоим инструментом диагностики на сломанном развёртывании.

  Минимум, на котором это проверено и который пинят наши ansible-роли:
  **VictoriaLogs v1.51.0, VictoriaMetrics v1.102.1**. `victorialogs_url` обязан
  указывать на VictoriaLogs; Loki-совместимая замена ручку не поймёт — и теперь
  получит отказ вместо молчаливого доверия. Что проба смотрит, а что нет: ВЕРСИЮ
  апстрима она не читает никогда — только то, разбирается ли ручка на тех путях,
  которые мы сужаем. Сборка новее или старше, но ручку разбирающая, пройдёт;
  версии выше — просто те, на которых это проверено.

  **Чего проба НЕ доказывает.** Она доказывает, что ручка РАЗБИРАЕТСЯ, а не что
  она ЭНФОРСИТСЯ. Апстрим, который параметр парсит, валидирует и семантически
  игнорирует, пробу пройдёт. Store-независимой пробы на энфорсмент не
  существует: «фильтр не вернул чужого» на пустом индексе неотличимо от «фильтр
  проигнорирован», а граница доступа не имеет права зависеть от того, есть ли
  прямо сейчас данные в индексе. Если у тебя не VictoriaLogs/VictoriaMetrics —
  проверь энфорсмент сам, сравнением «глобальный против привязанного» из пункта
  двумя выше.
- **Откат агента.** Агент версии ниже #994 не умеет искать логи в
  подкаталогах: уже размеченные файлы он не ротирует, не финализирует, не
  выметает ретенцией и не отдаёт live-tail'ом. Откатываешь агент — снеси или
  перенеси `{log_dir}/servers/*/*/` руками.
- **Свой шиппер — клади пару в СТРИМ-поля.** Если ты шипуешь логи не нашим
  vector'ом, `project` и `env` должны быть именно stream fields VictoriaLogs.
  Утечки неправильная разметка не создаёт (фильтр просто ничего не выберет),
  но оператор с привязанным ключом останется без своих логов. Брать пару из
  того, что дедик печатает в stdout, нельзя: тогда границу доступа
  контролировал бы сам дедик.
- **Метрики: видно только то, что несёт пару.** Master ставит её на
  `birdman_servers`, `birdman_versions`, `birdman_server_info`. Пер-серверные
  серии агента (`birdman_server_players`, `birdman_server_tick_ms`,
  `birdman_container_*`) несут её тоже — **с tracker #1008**, но только у
  дедиков, ЗАПУЩЕННЫХ после того апгрейда: пара чеканится в лейблы контейнера
  при create и задним числом не дописывается, поэтому уже работавший дедик
  продолжает эмитить один `server_id` и привязанному ключу невидим до
  перекрутки (такие серии доживают ретенцию VictoriaMetrics — 30 дней у
  референс-стека, тот же размен, что с нелейблованными строками логов выше).
  Пара ставится всегда ЦЕЛИКОМ, половинками не бывает. Платформенные агрегаты
  (`birdman_players_online`, `birdman_matches_running`,
  `birdman_node_capacity_slots`) — данные всего флота, пары в них нет вовсе. У
  привязанной сессии всё беспарное придёт пустым (`200` с пустой выдачей, не
  `403`), и учти, что ОДНОГО беспарного операнда хватает, чтобы обнулить всё
  выражение: панельная «утилизация %» гибнет на знаменателе
  `sum(birdman_node_capacity_slots)`, хотя числитель у неё собран на
  `birdman_servers` (замерено: глобальный `0.14`, привязанный `result:[]`).

**В каком порядке отвечает master.** Замерено на работающем мастере, а не
вычитано из исходников: в прошлой версии этого документа относительный порядок
`400` и `502` стоял наоборот, и узнать это можно только запуском. Сверху вниз,
выигрывает первое совпадение:

1. ключа нет → `401 unauthorized`;
2. у ключа нет скоупа `readonly`/`admin` → `403 scope readonly required`. Это
   про СКОУП, а не про привязку, и выигрывает у всего, что ниже, — в том числе
   у незаданного URL и у лежащего апстрима, поэтому по нему нельзя узнать,
   настроена ли проксия;
3. пара ключа непригодна к сужению (не проходит алфавит слага) → `403`,
   fail-closed. Единственный `403`, который порождает сама привязка, и через
   публичный API он недостижим: пара валидируется при создании ключа;
4. URL апстрима — ЯВНАЯ пустая строка → `503 metrics_unconfigured` /
   `logs_unconfigured`;
5. кривой `limit` у logs-проксии → `400 bad_request`. После `503` выше, но
   раньше ВСЕГО, что касается апстрима: такой запрос мастера не покидает. У
   metrics-проксий своего `limit` нет — для них это просто ещё один
   проброшенный query-параметр;
6. только для привязанного ключа — проба сужения (буллит выше):
   `503 *_narrowing_unsupported`, если ручку проглотили, и `502 upstream`, если
   вердикта нет;
7. боевой запрос не удался → `502 upstream`;
8. иначе `200` — привязанному ключу суженный его парой.

«Verbatim» верно для ДВУХ ручек из трёх: metrics-проксии пробрасывают
query-строку ровно в том виде, в каком она пришла, включая незнакомые параметры.
Logs-проксия не verbatim ни для кого — `limit` мастер ставит сам (деф. 1000) и
клампит потолком 10000, глобальному ключу ровно так же, как привязанному.

Референс стека мониторинга (VM + vmagent + vmalert + Grafana + бэкапы
Postgres) — ansible-роль `infra/roles/birdman_monitoring_dev`
(`infra/README.md`, раздел «Наблюдаемость + ops»). Нода может пушить метрики
своего агента в центральный VM сайдкаром-vmagent (`birdman_node_vmagent: true`
в host-блоке); свой VM — укажи `birdman_node_vm_remote_write_url: "http://<VM_HOST>:8428/api/v1/write"` там же (дефолт роли бьёт в наш оверлей-хаб).

⚠️ **Третий шов v1 (честно):** `add-node.sh` пишет ноде `birdman_node_vmagent:
true` и vector-сайдкар безусловно — если у тебя НЕТ VictoriaMetrics/VictoriaLogs
(чистый deploy/-мастер), эти шипперы будут слать в пустоту (буферят, игре не
мешают). Отключение: `birdman_node_vmagent: false` в host-блоке; vector-блок —
убрать `birdman_vl_sink_url` некуда (шиппер поднимется, но сообщения останутся
в диск-буфере) — вырезание vector целиком = прод-полировка.

## 5. Вывод ноды и снос

**Дренаж ноды** (перестать класть новые матчи, дать текущим доиграть):

```bash
curl -s -X POST http://127.0.0.1:8100/v1/nodes/<node_id>/drain   -H "Authorization: Bearer $KEY"
curl -s -X POST http://127.0.0.1:8100/v1/nodes/<node_id>/undrain -H "Authorization: Bearer $KEY"   # вернуть в строй
```

**Снос оверлея** (если Путь B — на КАЖДОМ боксе оверлея):

```bash
docker compose -f /opt/birdman/overlay/compose.yml down
sudo rm -rf /etc/birdman/overlay /opt/birdman/overlay
docker rmi birdman-overlay:local
```

UFW-правила оверлея (только на хабе): 4 правила с комментарием флота (`51827/udp`
и `in on birdman-wg0`). Осознанный вывод ноды из оверлея — прогон add-node.yml с
`-e birdman_overlay_allow_peer_removal=true` (иначе `-l`-гейт бережёт живой peer).

**Снос master-стека** (удаляет БД ; bind-файлы .env/secrets.key остаются на диске — удали руками):

```bash
cd birdman/deploy && docker compose down -v    # -v сносит том Postgres и secrets
```

## 6. Бекапы

Бекапы включены по умолчанию: master сам дампит свой Postgres (`pg_dump -Fc`)
каждые 6 часов в `/var/lib/birdman/backups` (том `backups` стека `deploy/`)
и держит 14 свежих дампов. Расписание, ретеншны и опциональный S3-совместимый
оффсайт (Backblaze B2 / Wasabi / AWS / MinIO) настраиваются в панели: вкладка
**Бекапы** — укажи endpoint/bucket/ключи, нажми *Проверить соединение*, затем
*Сделать бекап* для сквозной проверки. Оба ретеншна считают дампы, а не дни.

Restore: останови master, `pg_restore -d birdman --clean --if-exists <дамп>`
в свой Postgres, запусти master. Обратимые секреты едут в дампе только
AEAD-шифротекстом; ключ шифрования `secrets.key` никогда не покидает хост —
эскроу-копию храни отдельно (см. §1). Пошаговый runbook восстановления:
`docs/specs/ops.md §5`.

## 7. Безопасность: что торчит наружу

| Порт | Где | Наружу | Защита |
|---|---|---|---|
| `8444/tcp` | master-бокс | **да** | строгий mTLS (token-only Hello отвергается; Enroll-by-token → клиентский серт) |
| `8100` | master-бокс | **нет** — только `127.0.0.1` | наружу лишь через reverse-proxy/туннель |
| `20000–20050` tcp+udp | каждая нода | **да** | игровой трафик дедиков (UFW additive) |
| `19999/udp` | каждая нода | **да** | QoS-echo (единственный внешне-открытый служебный порт ноды) |
| `51827/udp` | хаб оверлея | да, если Путь B | WireGuard изолированного оверлея `10.77.0.0/24` |

Секреты и где они живут:

- **`secrets.key`** (master-бокс, `deploy/`, git-ignored, `0600`) — ключ
  шифрования секретов в БД at-rest. **Эскроу-копию в менеджер паролей**; потеря =
  секреты в БД не расшифровать.
- **admin-ключ** (`bmk_…`, скоуп `admin`) — печатается один раз при старте.
  Хранить как секрет; на master-боксе живёт в `/etc/birdman/master-admin.key`
  (`0600`, для регистрации нод).
- **`node_token`** — одноразовый, выдаётся `POST /v1/nodes`, живёт `0600` только
  на ноде; агент обменивает его на клиентский mTLS-серт при первом коннекте.
- **`POSTGRES_PASSWORD`** (`deploy/.env`, git-ignored).

Всё остальное (overlay-адреса `10.77.0.0/24`, WG-порт `51827`, игровые
`20000–20050`/`19999`) — не секреты: RFC1918 или публичные по дизайну.

### Ключ `matchmaking` и `player_id`

birdman аутентифицирует операторов, сервисы и ноды — **но не конечного игрока**,
и по дизайну не будет. `player_id` в matchmaking-тикете — непрозрачная строка от
вызывающего, master ей доверяет; нигде не персистится (колонки `player_id` нет
ни в одной таблице — игроки доходят до БД только счётчиком).

Поэтому ключ со скоупом `matchmaking` бьёт дальше, чем кажется: им можно завести
тикет с **любым** `player_id`, а зная `ticket_id` — прочитать чужой тикет (после
матча вместе с `host`, `port`, `match_id` и `join_token`) и отменить его; тикет с
чужим `player_id` вдобавок вытесняет собственный тикет этого игрока, пока тот ещё
стоит в очереди. Привязка ключа к паре `(project, env)` ограничивает это **между**
проектами и окружениями: она проверяется на всех трёх ручках тикетов, и тикет
чужой пары отвечает `404` — тем же телом, что и несуществующий `ticket_id`, ведь
`403` подтвердил бы, что чужой тикет существует. **Внутри** своей пары она не
ограничивает ничего: проверки владения тикетом нет вовсе, а глобальный
(непривязанный) ключ по-прежнему достаёт до всех проектов — привязка опциональна
by design. **Отдавай ключ
бэкенду игры, а не игровому клиенту**: бэкенд аутентифицирует игрока своим
механизмом, держит ключ у себя и заводит тикет с уже проверенным `player_id`.
Ключ, вшитый в клиент, — публичный секрет, и `player_id` тогда не гарантирует
ничего: лимит 5 rps на `player_id` — глушилка абьюза, а не граница безопасности.
`join_token` дыру не закрывает: он авторизует заход на конкретный дедик, а не
аутентифицирует игрока, и сегодня его никто не проверяет (сторона дедика — TODO).

Модель целиком — включая то, что остаётся за бэкендом (реконнект, выход игрока,
player-level стейт), — в `docs/specs/architecture.md`, раздел
«Модель доверия (trust boundaries)».
